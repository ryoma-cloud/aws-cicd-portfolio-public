# 共通事項

## 1. 作成対象外とする共通ドキュメント

本プロジェクトでは、ポートフォリオとしての目的、システム規模および文書管理上の実効性を踏まえ、以下の共通ドキュメントについては独立した成果物として作成しない。

- **執筆ルール**：`01_ドキュメント/README.md` に定めるドキュメント作成方針をもって代替する。
- **用語集**：対象システムの規模が限定的であり、必要な用語は各ドキュメント内で定義・説明可能であるため、独立した用語集は作成しない。

各工程固有の作成対象外ドキュメントについては、本READMEでは一律に定義せず、該当工程のREADMEまたは関連ドキュメントにおいて、その理由と併せて明示する。

## 2. 生成AI利用方針

本プロジェクトでは、生成AIとして **ChatGPT Work** を利用し、要件定義、設計、ドキュメント作成、実装、テストおよびレビューを支援・自動化する。

生成AIはリポジトリの内容を確認しながら複数工程を連続して進める開発支援エージェントとして利用する。特に、要件・設計の整理、成果物の作成・更新、実装、テスト、結果確認および修正までを可能な範囲で一連の作業として委譲し、人がすべての作業を逐次実施する場合と比較して、開発工数の削減と品質向上を図る。

一方で、生成AIとの対話内容、提案内容および一時的な判断は、それ自体を正式な要件・設計・成果物とは扱わない。採用した要件、設計、実装方針、判断結果その他のプロジェクト情報は、GitHub上のドキュメント、ソースコード、Terraform、テスト等へ反映し、最新かつ正式な情報はリポジトリで管理する。

### 2.1 ChatGPT Workを採用する理由

GPTを用いた開発支援環境として、ChatGPT Workを採用する。選定理由は以下のとおりである。

- **工程間の連続性**：要件整理・設計検討から、リポジトリの参照・更新、実装・テストまでを同一環境で扱えること。
- **導入費用の抑制**：既存のChatGPT契約を利用し、追加のサービス契約・導入負荷を抑えられること。
- **利用環境の統一**：生成AI製品の比較自体を目的とせず、開発・検証に作業を集中できること。

特定モデルの性能優位性を選定根拠とはせず、本プロジェクトに必要な作業範囲、既存契約、および運用の単純性を基準とする。

### 2.2 モデルの使い分け

モデルは、すべての作業で最高性能のモデルを固定的に使用するのではなく、作業の難易度、必要な推論量、処理時間および利用可能な実行枠を考慮して使い分ける。

- **高い推論能力を持つモデル**：複雑な要件整理、アーキテクチャ設計、重要な技術選定、批判的レビュー、複数ファイルにまたがる実装・テスト等、長時間かつ多段階の処理が必要な作業で使用する。
- **標準モデル**：文章修正、軽微なドキュメント更新、単純な調査、限定された設計確認等、比較的短時間で完結する作業で使用する。

モデル名や提供条件は将来変更される可能性があり、利用するモデルの指定は行わない。  
原則として、高い推論能力が必要な作業には高性能モデル、定型的・軽量な作業には標準モデルを使用する方針とする。

### 2.3 要件定義・設計工程での利用

要件定義および設計では、生成AIにユーザの指示をそのまま文書化させるのではなく、要求・要件の不足、矛盾、未決定事項、異常系および設計上の論点を検出させる。  

重要な設計判断では、関連する要件・制約を確認した上で、必要に応じて複数案、推奨案、採用理由、トレードオフおよび影響範囲を整理する。セキュリティ、信頼性、可用性、運用性、保守性、コスト等についても確認し、正常時に動作することだけをもって設計完了とはしない。要件、設計、実装、AWS上の実行状態、テスト結果は明確に区別し、生成AIによる推測を確認済みの事実として扱わない。

### 2.4 ドキュメント作成での利用

要件定義書、基本設計書、詳細設計書、テスト関連資料、運用資料、READMEその他のドキュメントについては、合意済みの内容を基に生成AIへ作成・更新を委譲する。  
生成AIには、単に文章を作成させるだけでなく、リポジトリ内の関連ドキュメントとの整合性、用語の統一、要件と設計の対応、変更による影響範囲を確認させる。  
重要な判断については、必要に応じて採用理由や代替案を記録し、第三者が「なぜこの設計としたのか」を説明できる状態を目指す。

### 2.5 実装・テストの自動化

実装およびテストでは、開発者がChatGPT Workへ可能な範囲で一連の作業を委譲する。
生成AIに、関連する要件・設計の確認、Terraformやアプリケーションコードの作成・修正、静的確認、テスト実行、結果確認、障害原因の調査および修正までを連続して実施させることで、長時間の反復作業を自動化する方針とする。  
ただし、生成AIがコードを生成したことと、実装が完了したこと、AWS上で正常に動作していること、要件を満たすことは同一ではない。  
実装完了やテスト完了は、実際の変更内容およびテスト結果を確認した場合にのみ判断する。

### 2.6 設計開発エージェント

設計開発エージェントは、要件定義担当、システムアーキテクトとして、要件定義から設計、実装、テストまでの一連の開発作業を支援する。  

ユーザの指示を単に文書化するのではなく、要求・要件の不足、矛盾、未決定事項および設計上の論点を整理し、必要に応じて選択肢、推奨案、採用理由およびトレードオフを提示する。また、合意済みの内容に基づき、ドキュメント、Terraform、アプリケーションコード、テストその他の成果物を作成・更新する。

**主なプロンプト方針**

> 要件定義担当、システムアーキテクトとして、要求、要件、設計、実装およびテストの整合性を確認しながら開発を推進する。不足事項、矛盾または未決定事項を検出した場合は明示し、必要に応じて選択肢、推奨案、根拠およびトレードオフを提示する。確定した内容はリポジトリへ反映し、実装後は主要な要件をテストにより確認する。

プロンプト詳細： [02_設計開発エージェント.md](02_設計開発エージェント.md)

### 2.7 レビューエージェント

レビューエージェントは、独立したレビュアー、システムアーキテクトとして、設計開発エージェントとは独立した観点から、要件、設計、実装、テストおよび関連ドキュメントの妥当性を検証する。  

既存の設計判断や実装を前提として無条件に肯定せず、要件漏れ、矛盾、根拠不足、過剰設計、過少設計、セキュリティ、信頼性、運用性、保守性、コスト等の観点から問題の有無を確認する。  
また、要件、設計、実装、実行環境、テスト結果を明確に区別し、推測を確認済みの事実として扱わない。指摘事項については、必要に応じて重要度、根拠、影響、推奨対応および代替案、トレードオフを整理し、変更による複雑性や実装工数が、その効果に見合うかについても評価する。

**主なプロンプト方針**

> 独立した設計レビュー担当として、既存の要件、設計、実装およびテスト結果を批判的に検証する。要件、設計、実装、実行環境の状態、テスト結果を明確に区別し、推測を確認済みの事実として扱わない。問題点については、重要度、根拠、影響および改善案を明示し、より単純または妥当な代替案が存在する場合は、その長所・短所や判断上の得失と併せて比較する。

プロンプト詳細： [03_レビューエージェント.md](03_レビューエージェント.md)
