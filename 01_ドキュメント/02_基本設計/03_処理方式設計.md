# 処理方式設計

## 1. 処理分担

| 処理 | 担当 | 役割 |
| --- | --- | --- |
| 社員情報受付 | 社員情報受付Lambda | 入力検証・SQS登録・受付応答 |
| 社員情報登録 | 社員情報登録Lambda | 非同期登録・入館証番号採番 |
| 入館証発行依頼 | 入館証発行依頼Lambda | 入館証発行依頼ファイル作成・S3保存・送信要求 |
| 入館証発行依頼結果反映 | 入館証発行依頼結果反映Lambda | DB状態反映・S3配置変更 |

## 2. 社員情報受付・登録

### 2.1 処理対象

ID管理システムから随時連携される社員情報を対象とする。受付単位は1要求につき1人分とする。

### 2.2 処理フロー

1. 社員情報受付Lambdaが社員情報を検証し、連携受付日時を付与してSQSへ登録する。
2. SQS登録完了後、ID管理システムへ`202 Accepted`を返す。
3. 社員情報登録LambdaがSQSから要求を受け取り、新規対象に入館証番号を採番してDBへ登録する。

API受付とDB登録は非同期で行う。`202 Accepted`は要求の受付完了を意味し、DB登録の完了を意味しない。

### 2.3 登録方針

社員番号をキーに重複登録を防止する。同じ社員番号を受信した場合は、氏名・所属会社名を比較する。

| 既存データとの関係 | 処理方針 |
| --- | --- |
| 社員番号が未登録 | 入館証番号を採番し、新規登録する |
| 社員番号が登録済みで、氏名・所属会社名が一致 | 既存データを維持し、正常終了する |
| 社員番号が登録済みで、氏名または所属会社名が不一致 | 既存データを維持し、要求をDLQへ隔離して監視通知する |

同時処理・再処理でも、同一社員の対象を重複登録しない。入館証番号の重複・再利用は許容せず、欠番は許容する。

### 2.4 異常時の処理

| 発生事象 | 処理方針 |
| --- | --- |
| SQSへの登録に失敗 | 監視通知およびID管理システムへエラー応答を返し、障害解消後、ID管理側から再連携する |
| DB登録に失敗 | 自動再試行し、継続失敗時に要求をDLQへ隔離して監視通知する |

入力不正・SQS登録失敗時の受付応答は、[外部連携方式設計](02_外部連携方式設計.md)に定める。

## 3. 入館証発行依頼

### 3.1 処理対象

日次処理で、以下を対象とする。

| 処理 | 対象 |
| --- | --- |
| 入館証発行依頼ファイル作成 | 連携受付日が前日以前で、状態が`REQUESTED`かつ送信ファイル名が未設定のレコード |
| 送信要求 | S3の`transfer/`に保存されている入館証発行依頼ファイル |

### 3.2 処理フロー

1. 入館証発行依頼Lambdaが対象データから入館証発行依頼ファイルを作成し、S3の`transfer/`へ保存する。
2. `transfer/`に保存されている入館証発行依頼ファイルについて、SFTP Connectorへ送信要求する。
3. SFTP送信結果は、入館証発行依頼結果反映Lambdaで非同期に反映する。

入館証発行依頼Lambdaは送信要求までを対象とし、SFTP送信結果は反映しない。

### 3.3 異常時の処理

| 発生事象 | 処理方針 |
| --- | --- |
| 入館証発行依頼ファイル作成に失敗 | 監視通知し、その他保存済み入館証発行依頼ファイルの送信要求に進む |
| 個別入館証発行依頼ファイルの送信要求に失敗 | 監視通知し、他の入館証発行依頼ファイルの送信要求を続ける |

ファイル準備失敗時のデータ保持方針は[データ基本設計](05_データ基本設計.md)、復旧方針は[運用監視基本設計](07_運用監視基本設計.md)に定める。

## 4. 入館証発行依頼結果反映

### 4.1 処理対象

SFTP Connectorによる初回送信・再送の送信結果を対象とする。

### 4.2 処理フロー

1. 入館証発行依頼結果反映LambdaがEventBridge経由でファイル送信結果を受け取る。
2. ファイルに対応するDBレコードへ、送信結果を反映する。
3. DBで反映可否を判定したうえで、送信結果に応じて入館証発行依頼ファイルをS3の`success/`または`failed/`へ配置変更する。

送信成功を確定扱いとし、成功確定後に届く失敗結果ではDB・S3を失敗状態へ戻さない。同じ成功結果の再実行は許容し、未完了のS3配置を復旧できるようにする。

### 4.3 異常時の処理

| 発生事象 | 処理方針 |
| --- | --- |
| DB反映・反映可否の確認に失敗 | S3配置変更を保留し、自動再試行する。最終失敗時に保存・監視通知する |
| S3配置変更に失敗 | 自動再試行し、最終失敗時に保存・監視通知する |

DBとS3の一時的な不一致を許容し、保守対応で復旧する。

### 4.4 失敗情報の保存

送信結果の配信失敗と、結果反映処理の実行失敗は、別のSQSへ保存する。

| 失敗箇所 | 保存先 | 保存する情報 |
| --- | --- | --- |
| EventBridgeからLambdaへの配信 | EventBridgeターゲットDLQ | 配信できなかった送信結果イベント |
| Lambdaによる結果反映処理 | 実行失敗用SQS | 結果反映に失敗した入館証発行依頼結果情報 |

復旧方針は、[運用監視基本設計](07_運用監視基本設計.md)に定める。

## 5. 状態・ファイル管理

### 5.1 DBの状態管理

| 状態 | 意味 |
| --- | --- |
| `REQUESTED` | DB登録済みで、初回のSFTP送信結果反映待ち |
| `SENT` | SFTP送信完了 |
| `SEND_FAILED` | SFTP送信失敗 |

送信中専用の状態は設けない。初回送信中は`REQUESTED`、再送中は`SEND_FAILED`を維持する。

| 現在の状態 | SFTP送信結果 | 反映後の状態 |
| --- | --- | --- |
| `REQUESTED` | 成功 | `SENT` |
| `REQUESTED` | 失敗 | `SEND_FAILED` |
| `SEND_FAILED` | 成功 | `SENT` |
| `SEND_FAILED` | 失敗 | `SEND_FAILED` |
| `SENT` | 成功 | `SENT`（未完了の成功配置は再実行可能） |
| `SENT` | 失敗 | `SENT`を維持し、S3配置も変更しない |

### 5.2 S3のファイル配置

| 配置先 | 用途 |
| --- | --- |
| `transfer/` | 定時送信の対象となる入館証発行依頼ファイルを保存する |
| `success/` | SFTP送信に成功した入館証発行依頼ファイルを保存する |
| `failed/` | SFTP送信に失敗した入館証発行依頼ファイルを保存する |

DB登録直後はファイルが存在しないため、DB状態とS3配置は分けて管理する。結果反映に失敗した場合は一時的に両者が一致しない場合がある。

### 5.3 DBと入館証発行依頼ファイルの対応

送信ファイル名でDBレコードと入館証発行依頼ファイルを対応付ける。S3配置変更後も対応を維持し、DBにはS3パスや送信IDを保持しない。

詳細なデータ管理方針は、[データ基本設計](05_データ基本設計.md)に定める。
