# データ基本設計

## 1. 管理方式

社員情報・入館証番号・入館証発行依頼状況・入館証発行依頼ファイルとの対応を、単一の入館証発行対象テーブルで管理する。  
送信管理・送信試行履歴の別テーブルは設けず、過去の送信試行とエラー詳細はログで確認する。

## 2. 主要項目

| 項目 | 内容・付与元 |
| --- | --- |
| 社員番号 | ID管理システムから受信、主キー |
| 氏名 | ID管理システムから受信 |
| 所属会社名 | ID管理システムから受信 |
| 入館証番号 | 本システムが一意に採番 |
| 処理状況 | 入館証発行依頼待ち（`REQUESTED`）、入館証発行依頼済み（`SENT`）、入館証発行依頼失敗（`SEND_FAILED`） |
| 送信ファイル名 | 入館証発行依頼ファイルとの対応。ファイル作成前に割り当て、配置変更後も維持 |
| 連携受付日時 | API受付時に本システムが付与 |
| 更新日時 | レコード内容最終更新日時 |

新規登録時は処理状況を`REQUESTED`、送信ファイル名を未設定とする。`SENT`はSFTP送信完了を表し、入館証の発行完了を表さない。状態遷移は[処理方式設計](03_処理方式設計.md)に従う。

## 3. 一意性・更新の方針

| 対象 | 方針 |
| --- | --- |
| 社員番号 | 同時処理・再処理でも同一社員の対象を重複登録しない |
| 入館証番号 | 重複・再利用を許容しない。欠番は許容 |
| 同じ社員番号・同内容 | 追加登録・再採番をせず、既存データを維持 |
| 同じ社員番号・異内容 | 既存データを維持し、DLQ隔離・監視通知 |
| 内容比較 | 氏名・所属会社名を比較し、システム付与日時は含めない |

## 4. ファイル・ステータス管理

### 4.1 ファイル名とDBの対応

入館証発行依頼ファイルはCSV形式とし、ファイル名には処理単位を識別できる日時情報を含める。  
新規ファイルの名前は重複させず、再送・配置変更では名前と内容を維持する。

ファイル作成前に、対象レコード全件へ同じ送信ファイル名を一括で割り当てる。  
割当途中の失敗は全件取り消す。送信結果もファイル単位で全件一括更新する。

DBにはファイル名を保持し、S3パスは保持しない。具体的なファイル名の書式・日時精度は詳細設計に記載する。

### 4.2 ステータス

| ステータス | 意味 |
| --- | --- |
| `REQUESTED` | DB登録済みで、初回のSFTP送信結果反映待ち |
| `SENT` | SFTP送信成功。入館証の発行完了ではない |
| `SEND_FAILED` | SFTP送信失敗 |

初回送信中は`REQUESTED`、再送中は`SEND_FAILED`を維持する。

### 4.3 ファイルパス

| S3パス | 意味 |
| --- | --- |
| `transfer/<ファイル名>` | 日次処理で送信するファイル |
| `success/<ファイル名>` | SFTP送信に成功したファイル |
| `failed/<ファイル名>` | SFTP送信に失敗したファイル。手動再送の対象 |

DB更新とS3配置変更は別の操作として行う。成功確定後の失敗結果による状態後退を防ぐため、DBで反映可否を確認してからS3を操作する。DBで判定できない場合はS3変更を保留する。障害による不一致は再試行・保守対応で復旧する。

## 5. 日時・保持

業務日時はJSTで統一する。送信・復旧に必要なファイルは、対応が完了するまで削除しない。ファイル復元などの対応は[運用監視基本設計](07_運用監視基本設計.md)に定める。

DB・ファイル・ログ・バックアップの具体的な保持期間、削除条件、日時精度は詳細設計または運用設計に記載する。
