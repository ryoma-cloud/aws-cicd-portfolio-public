# 運用監視基本設計

## 1. 運用方針・責任

CloudWatch・Security Hub・GuardDuty・Inspector・Config・AWS Budgets等のサービスを使用し、業務・基盤の異常や重大なセキュリティ上の問題を検知した場合、または予算の通知額に到達した場合にメール通知し、保守担当者が内容を確認して対応する。

ユーザの操作は状況参照のみとし、再送・DB訂正等の保守操作を画面に設けない。受付済み情報の変更・訂正・取消・差し替えは対象外とする。

## 2. 監視・通知

監視は、業務処理の最終失敗、基盤の継続異常、失敗情報の保存経路、日次処理の未完了を組み合わせる。CPU等の基盤指標だけでは、処理未起動や送信結果の未反映を検知できないためである。

### 2.1 通知の考え方

自動再試行で回復する途中失敗を一律にメール通知しない。登録・結果反映はDLQ／最終失敗キューを監視し、結果反映Lambdaの通常のErrorsを即時通知条件にしない。受付・バッチ等の最終失敗は独自メトリクスで通知する。強制終了・スロットリング・失敗情報保存経路の異常は別に監視する。

通常のECS停止・ローリング更新は障害扱いしない。成功確定後に届いた失敗結果は正常に省略し、SFTP失敗を再通知しない。ALARMへの遷移で通知し、継続障害の同一内容を毎分メール送信しない。数値条件・評価期間・メトリクス定義は[CloudWatch詳細設計](../03_詳細設計/01_基盤/13_AWS_CloudWatch.md)、宛先・配信経路は[SNS詳細設計](../03_詳細設計/01_基盤/15_AWS_SNS.md)にまとめる。

日次処理後に、当日の処理完了記録と前日以前の要求の送信状態を確認する。完了記録なし、未処理残存、確認失敗はSNSへ通知し、翌朝に保守担当者が調査・復旧する。監視側を含む両スケジュールの同時無効化・一時環境削除中は検知対象外とする。通知集約・月次報告は設けない。

### 2.2 監視の成立条件・範囲

SNSメール購読の確認完了とテストメール受信を運用開始条件とする。定時運用では日次処理とその完了確認を対で有効化し、初回の実行履歴・完了記録・確認結果を確認する。

欠測を正常扱いするアラームは、処理のない時間帯の誤通知を抑えるためのものであり、メトリクス未着を正常稼働の証明とはしない。日次完了確認も同じrequest-batch Lambdaを使うため、完全に独立した外形監視ではない。外部からの常時疎通、通知未達、両スケジュールの同時無効化を自動検知する機構は設けない。

ALARM遷移通知の抑制はCloudWatchアラームに対する方針である。ECS・RDS・Security Hubからのイベント通知は別経路であり、更新・再配信による重複通知があり得る。Security Hubの通知対象はACTIVEかつNEWのHIGH/CRITICALに限定し、全ての未解決所見を再通知する方式とはしない。

## 3. 障害対応・復旧

| 状況 | 復旧方式・完了判断 |
| --- | --- |
| CSV作成・保存失敗 | DBの割当済みファイル名を基に同名・同内容のCSVを再作成し、保存完了を確認 |
| SFTP失敗 | 原因解消後、failed/に保持したCSVを手動再送し、Connector成功・DB=SENT・S3=success/を確認 |
| DB結果反映失敗 | 保存した元の転送結果を用いてDBのみ再反映し、正常反映後に保存メッセージを処理済みとする |
| S3配置不一致 | 実際の送信結果とDB判定に基づき元・先の内容を照合し配置復旧。S3残存だけで転送失敗と判断しない |
| 成功確定後の失敗結果 | SENTと成功配置を維持。同じ成功結果の再実行で未完了の配置復旧を許容 |
| DB判定不能 | S3変更を保留し再試行。DB判定が回復するまで失敗配置へ移さない |
| 単一タスク・DB・AZ障害 | 標準の自動復旧後にヘルス・DB接続・業務疎通を確認 |
| DB論理障害・過去時点復元 | 影響と復元先を確認し、復元DBとS3・外部送信結果の整合性を確認してから業務を再開 |

転送要求の成否が不明な場合は履歴を確認して再実行を判断する。転送成功後にtransfer/へ残ったCSVは次回日次処理までに配置を復旧する。DB・S3の修復とSFTP再送を区別し、成功済みCSVを修復目的で再送しない。

過去時点復元後の自動照合・全入力の完全再現機構は設けない。保守操作はGitHub Actions・保守用権限を入口とし、具体操作と確認条件は[運用手順書](../05_運用/02_運用手順書.md)に従う。

## 4. ログ管理・保守

| 対象 | 管理方針 |
| --- | --- |
| アプリ・サービスログ | 処理名・識別子・処理段階・成否・エラーを記録し、社員番号・ファイル名を手掛かりに追跡可能とする |
| 機密情報・個人情報 | Secret・鍵・署名・CSV本文・不要な氏名等をログへ出力しない |
| 日時 | 業務・画面・アプリログはJSTとし、AWSが生成する時刻形式は変更しない |
| CloudWatch Logs | アプリ・対向システム・API・Web・DB・転送処理等を稼働中90日保持し、一時環境削除時には対象ログを削除 |
| 保守・更新 | AWSマネージド基盤の保守はAWSに委ね、アプリ・依存ライブラリ・カード発行業者のEC2のOSは保守担当者が更新 |
| 認証情報・SFTP鍵 | 保守変更時に更新し、更新後の接続を確認。定期的な自動ローテーションは対象外 |

未完了や復旧対象のCSVは、対応完了まで削除しない。計画保守ではサービス全停止を避け、DB切替・再接続中の一時的なエラーは許容する。

DB・CSVのバックアップ方式と保持期間は[基盤・非機能基本設計](06_基盤・非機能基本設計.md)に定める。本書では監視・復旧判断・保守上の取扱いを定め、具体的な操作は[運用手順書](../05_運用/02_運用手順書.md)に従う。

## 5. 構築・変更・切り戻し

AWS構成はTerraformで管理し、GitHub ActionsのCIで基本的な静的検証を行う。環境の作成・変更・削除は手動ワークフローから実行し、GitHub ActionsのOIDC認証を使用する。環境間の操作は競合しないよう直列化する。

`plan`で事前に差分を確認し、別の実行で`apply`を選択する。`apply`時はその実行内で新しいplanを生成して適用するため、事前planとの一致は保証しない。初回の一時環境planは先行構築範囲に限られ、残りの構築とDB変更は`apply`内で段階的に計画・適用する。各段階の差分・実行結果はワークフローログで確認する。詳細は[ワークフロー概要](../../03_ワークフロー/01_ドキュメント/01_ワークフロー概要.md)に定める。

Webはローリング更新で正常タスクを維持する。Lambda・DB変更はインターフェースとスキーマの互換性を確認し、異常時には正常なアプリケーション版へ切り戻す。DBデータの復元が必要な場合は整合性を確認して再開を判断する。切り戻し対象のイメージ・版情報と変更結果を記録する。

CIやTerraformの適用成功のみを業務正常と判定せず、必要な業務試験・接続確認は別途実施する。

## 6. 環境・費用管理

環境は1つとし、費用抑制のため未使用時は一時リソースを削除する。常設・一時の区分と削除対象を分けて管理する。

| 区分 | 管理対象 |
| --- | --- |
| 常設 | VPC・基本経路、ECRリポジトリ、予算監視、Config証跡保管等 |
| 一時 | ECS・Aurora、業務用S3、外部連携・対向システム、監視・セキュリティ設定、Interface VPC Endpoint等 |
| 環境削除後も保持 | Terraform backend用S3・state、OIDC実行基盤等 |

一時環境の削除前には未処理データと復旧対象を確認する。削除したDB・CSV・ログの引継ぎは行わず、再構築時は必要なデータを再投入する。これは稼働中障害での復旧方針とは区別する。再開時には依存サービス、監視、業務接続、未処理状況を確認する。

AWS Budgetsで利用料金を通知するが、課金上限や自動停止は保証しない。費用評価にはDB・Endpoint・Transfer Family・セキュリティサービスを含める。具体的な保持条件、時間帯、停止・再開手順は[運用設計書](../05_運用/01_運用設計書.md)に定める。
