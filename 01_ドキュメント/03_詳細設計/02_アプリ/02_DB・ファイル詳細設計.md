# DB・ファイル 詳細設計

## 1. テーブル定義

database=portfolio、schema=badge、table=card_requests。業務テーブルは1つ。ユーザ情報・履歴・送信管理の別テーブルは作らない。SQL中の省略名card_requestsはsearch_path=badge,pg_catalogにて解決する。

| 項目 | 物理名 | 型 | NULL | 制約・初期値 |
| --- | --- | --- | --- | --- |
| 社員番号 | employee_id | varchar(6) | 不可 | PRIMARY KEY |
| 氏名 | employee_name | varchar(100) | 不可 | 空白のみ不可 |
| 所属会社名 | company_name | varchar(100) | 不可 | 空白のみ不可 |
| 入館証番号 | badge_number | varchar(16) | 不可 | UNIQUE、英字1文字＋数字15桁 |
| 処理状況 | status | varchar(11) | 不可 | 初期REQUESTED、3状態CHECK |
| 送信ファイル名 | send_filename | varchar(64) | 可 | 初期NULL、規定名CHECK |
| 連携受付日時 | received_at | timestamptz | 不可 | 受付Lambdaの値 |
| 更新日時 | updated_at | timestamptz | 不可 | 登録時CURRENT_TIMESTAMP |

入館証番号は英字1文字＋数字15桁の計16文字（例：A012345678912345）とする。採番の初期方式はアプリで英大文字1文字と15桁ゼロ埋めの乱数を生成し、DBの一意制約で重複を許可しない。社員番号・入館証番号とも文字列として保持し、先頭ゼロを欠落させない。独立したDB内部ID・作成日時・送信日時・再送回数は追加しない。日時の物理型は時点を保持し、セッション・画面・アプリログでJSTに統一する。

### 1.1 DDL

```sql
CREATE SCHEMA IF NOT EXISTS badge;
REVOKE CREATE ON SCHEMA public FROM PUBLIC;

CREATE TABLE badge.card_requests (
  employee_id varchar(6) PRIMARY KEY
    CHECK (employee_id ~ '^[0-9]{6}$'),
  employee_name varchar(100) NOT NULL
    CHECK (length(btrim(employee_name)) > 0),
  company_name varchar(100) NOT NULL
    CHECK (length(btrim(company_name)) > 0),
  badge_number varchar(16) NOT NULL UNIQUE
    CHECK (badge_number ~ '^[A-Za-z][0-9]{15}$'),
  status varchar(11) NOT NULL DEFAULT 'REQUESTED'
    CHECK (status IN ('REQUESTED','SENT','SEND_FAILED')),
  send_filename varchar(64)
    CHECK (send_filename ~ '^request_[0-9]{14}_[0-9a-f]{32}[.]csv$'),
  received_at timestamptz NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX card_requests_filename_idx
  ON badge.card_requests(send_filename)
  WHERE send_filename IS NOT NULL;
CREATE INDEX card_requests_unassigned_idx
  ON badge.card_requests(received_at, employee_id)
  WHERE status='REQUESTED' AND send_filename IS NULL;
CREATE INDEX card_requests_received_idx
  ON badge.card_requests(received_at DESC, employee_id ASC);
```

入力の制御文字・全項目検証は共通validatorで行い、DB CHECKと役割を分担する。スキーマDDLはマイグレーションファイルで管理する。同じDDLを毎回無条件実行しない。

## 2. DBユーザ

| ユーザ | 権限 | Secret名 |
| --- | --- | --- |
| portfolio_admin | DDL・ユーザ作成、通常業務に不使用 | Aurora管理Secret ARN |
| badge_app | schema USAGE、table SELECT/INSERT/UPDATEのみ | portfolio/card/db-app |
| badge_web | schema USAGE、table SELECTのみ | portfolio/card/db-web |

PUBLICのtable権限を取り消す。badge_appにDELETE/CREATE、badge_webに更新系権限を付けない。パスワードは構築プログラムで生成しSecretへ保存、Terraform state・ログに出さない。ホストはWriter/Readerを環境変数で分離する。

## 3. SQL・トランザクション

| 処理 | 条件・処理単位 |
| --- | --- |
| 新規登録 | employee_idをキーにINSERT。競合時DO NOTHING後SELECTで業務項目比較 |
| ファイル割当 | BEGIN→対象行ロック→同じファイル名へ一括UPDATE→COMMIT |
| 結果反映 | 第1トランザクションでfilenameの対象行をロックし、成功確定条件を判定して必要なDB更新をCOMMIT。通常起動では第2トランザクションで同じ行を再ロックし、状態を再確認した上でS3配置を実行。DBのみの保守起動は第2段階を省略。SELECT対象0件は異常、同状態のUPDATE 0件は正常 |
| 一覧参照 | 検索条件のCOUNTと50件取得をReaderの同じREAD ONLY REPEATABLE READトランザクション内で実行 |
| CSV復元用抽出 | filenameでSELECT、employee_id ASC。更新しない |

結果反映のS3操作はDBトランザクションと一括確定されない。S3配置に失敗しても第1段階のDB結果は維持し、同じ結果の再処理で配置を復旧する。成功確定後の失敗結果と並行処理は[Lambda処理仕様](01_Lambda処理仕様.md)の第5.3節に従う。

### 3.1 ファイル割当

```sql
BEGIN;
WITH target AS (
  SELECT employee_id
  FROM badge.card_requests
  WHERE status = 'REQUESTED'
    AND send_filename IS NULL
    AND received_at < %(cutoff)s
  ORDER BY received_at, employee_id
  LIMIT 10000
  FOR UPDATE SKIP LOCKED
)
UPDATE badge.card_requests AS r
SET send_filename=%(filename)s, updated_at=CURRENT_TIMESTAMP
FROM target AS t
WHERE r.employee_id=t.employee_id
RETURNING r.employee_id,r.employee_name,r.company_name,r.badge_number;
COMMIT;
```

RETURNINGの順序に依存せずCSV作成前にemployee_id順へ並べる。割当済みレコードの氏名等は通常処理で変更しないため、手動復元でも同じ内容を再現できる。

### 3.2 復元用SELECT

```sql
SELECT employee_id,employee_name,company_name,badge_number
FROM badge.card_requests
WHERE send_filename=%(filename)s
ORDER BY employee_id;
```

0件、別名への差し替え、転送済みファイルの無条件上書きを許容しない。CSVの自動再作成ツールは作らず、保守担当者が本書の形式で作成・照合する。

## 4. CSV物理仕様

| 項目 | 採用仕様 |
| --- | --- |
| ファイル名 | request_YYYYMMDDhhmmss_<uuid4.hex>.csv、日時はJST、UUID32桁 |
| 例 | request_20261016010000_1234567890abcdef1234567890abcdef.csv |
| 新規名 | 日時とUUIDで生成、既存名を上書きしない |
| 文字コード / BOM | UTF-8 / なし |
| ヘッダー | employee_id,employee_name,company_name,badge_number |
| 列順 | 上記4列固定 |
| 改行 | CRLF、最終行にも付与 |
| 区切り / 引用 | カンマ、二重引用符、QUOTE_MINIMAL、引用符を二重化 |
| 行順 | employee_idの昇順 |
| NULL / 空値 | 4列はNULL・空値なし |
| 最大 | 1ファイル10000行、完成バイト列16 MiB |
| checksum | 全バイト列のSHA-256（小文字hex）、S3 metadata sha256へ保存 |

```csv
employee_id,employee_name,company_name,badge_number
000001,テスト 太郎,テスト株式会社,A012345678912345
```

上記コード表示の改行ではなく、生成バイト列はCRLFとする。カンマ・引用符を含む氏名等はCSVライブラリで引用する。Excel用の値書換えは行わず、対向SFTPへ原値を保持する。

## 5. データ保持

DBレコードは一時環境が存続する間は全件保持。連携受付後の訂正・削除・再発行は初期範囲外。S3は09、ログは13、DBバックアップは06の保持値に従う。一時環境を削除して再投入するテストデータと、稼働中の復旧データは区別する。

## 6. 日次未処理の件数照会

```sql
SELECT count(*) AS total
FROM badge.card_requests
WHERE received_at < %s AND status <> 'SENT';
```

パラメータは確認当日00:00 JST。DBの照会失敗を0件へ置換しない。既存の業務テーブルを使用し、監視用テーブルは追加しない。
