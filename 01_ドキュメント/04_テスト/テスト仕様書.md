# テスト仕様書

現行CIはPython構文、ワークフロー模擬実行、Terraform fmt/validateを検証する。構築変更・削除は02_環境操作、状態確認は03_Terraform状態確認、業務・復旧・自動増減・監視設定等は構築済み環境に対して`04_テスト`の独立試験で行う。既存項目の網羅範囲を削らず、実行入口と実証範囲を区別する。要件検証は環境を自動作成・削除しない。監視設定照合を全アラーム発報・配送・実メール受信の成功と扱わない。入力と実行範囲は[ワークフロー利用ガイド](../05_運用/03_ワークフロー利用ガイド.md)に従う。

## 1. 目的・対象

入館証システムの要件・基本設計・詳細設計に基づき、業務機能、データ整合性、外部連携、基盤構成、構築・変更管理、監視・運用を確認する。

社員情報受付は署名付きHTTP API → SQS → DB、入館証発行依頼は日次CSV → AWS Transfer Family SFTP Connector、送信結果反映はEventBridge → Lambda → DB・S3を対象とする。ID管理システムとカード発行業者のモックを対向として使用する。

社員番号は数字6桁、入館証番号は英大文字1文字＋数字15桁とする。業務状態は`REQUESTED`・`SEND_FAILED`・`SENT`とし、送信成功確定後の失敗結果ではDB・S3を失敗状態へ戻さない。

## 3. 確認観点・判定基準

### 3.1 入力検証・社員情報受付

社員番号の桁数・型・先頭ゼロ、氏名・会社名の長さ・空白・制御文字・Unicode、JSON形式、Base64本文、HTTP要求形式を確認する。不正入力は定義したエラーで拒否し、SQS・DBへ副作用を発生させない。

正常時はSQSへの登録完了後にHTTP 202を返す。受付応答とDB登録完了を分けて確認する。SQS登録失敗時の応答、SDK再試行上限、最終失敗メトリクス、秘密値を含まないログを確認する。

### 3.2 社員情報登録・DB

同一社員・同一内容の再受付で既存情報を維持し、異内容は上書きせず失敗として扱う。同時登録でも社員行は1件とし、入館証番号の形式・一意性、DB制約、マイグレーションの再適用・checksum検証を確認する。

SQSバッチの部分失敗では失敗したメッセージだけを再処理対象とする。登録継続失敗時のDLQ隔離、原因解消後のredrive、既存データの維持を確認する。

### 3.3 対向モック

ID管理モックの入力構造、件数上限、HTTP応答別の判定、通信障害、残り実行時間、再試行・リダイレクト制御を確認する。送信した社員情報を勝手に変換せず、氏名等をログへ出力しない。

カード発行業者の対向ではSFTP受信先と受信ファイルを確認し、送信元との内容一致をSHA-256で判定する。

### 3.4 日次CSV・完了確認

01:00 JSTの日次処理は、当日00:00 JSTより前の受付で、REQUESTEDかつファイル未割当のレコードを抽出する。並行実行時の二重割当防止、社員番号順、UTF-8 BOMなし、引用符の二重化、CRLF、サイズ上限、SHA-256、上書き防止条件を確認する。

CSV準備失敗時も保存済みtransfer/の送信要求を継続する。個別失敗・時間不足・件数上限を成功扱いにしない。割当後に準備失敗したデータは、同一ファイル名で復旧できることを確認する。

CSV準備と転送要求が正常な場合に当日の完了記録を保存し、0件日次も記録する。03:00 JSTの確認では完了記録と未処理件数を確認する。記録欠落・旧日付・読取不能、未処理残存、DB確認失敗を区別し、専用FinalFailureメトリクスを通知先へ接続する。確認処理ではDB・S3を更新せず、CSVを再送しない。

日次実行・完了確認のSchedulerは同時に有効化し、JSTの時刻設定を確認する。手動実行ではSchedulerとの競合防止と戻り値の業務判定を確認する。

### 3.5 送信結果反映・成功確定

イベントの送信元・account・region・Connector・操作・bucket・key・結果種別を検証し、不正イベントでDB・S3を変更しない。

DB反映・状態再確認をS3配置変更に先行させる。DB障害時はS3変更を保留し、DB成功後のS3失敗ではDB結果を維持する。同じ結果の再実行で未完了処理を復旧し、正常に収束することを確認する。

SENTは成功確定とし、成功後に届く新旧の失敗結果でDB・S3を戻さない。同じ成功結果は未完了のS3配置を復旧できるものとする。並行する結果反映は行ロックで順序を制御し、成功確定後の失敗配置を防止する。省略した失敗結果ではTransferFailedを発報しない。

非同期実行は初回＋最大2回の再試行を確認する。EventBridge配信不能はターゲットDLQ、Lambda実行失敗は実行失敗SQSに保存し、それぞれ監視する。

### 3.6 S3配置・再送・保守復旧

元のみ、元先両方、先のみ、両方なし、内容不一致、コピー後検証失敗、AccessDeniedの各状態を確認する。存在確認・SHA-256・長さ確認に成功した場合だけ元ファイルを削除する。

再送はfailed/の規定名CSVを対象とし、0件、複数件、個別失敗、ページング、上限・残り時間、確認フラグを確認する。送信要求時にDB・S3を更新せず、要求受理と転送完了を区別する。

保存結果の再反映はdelivery・execution双方の形式に対応し、指定MessageIdのイベントをDBのみ同期実行する。FunctionErrorなし、ok=true、db=OK、s3=SKIPPED、filename一致をすべて確認してからSQSメッセージを削除する。不正応答、対象未取得、DB失敗、削除失敗を成功扱いにしない。CSV復元・S3配置復旧は割当情報と実転送結果に照合し、不要な再送を発生させない。

### 3.7 Web照会・可用性

社員番号完全一致、氏名部分一致、状態のAND条件、LIKE特殊文字・SQL注入文字列、ページング、0件表示、HTMLエスケープ、先頭ゼロ、JST表示、no-storeを確認する。

不正検索は400でDBを参照せず、DB利用不可は詳細を漏らさず503とする。生存確認とDB接続確認を区別する。実機判定では入力欄や選択肢の文字列でなく、該当社員行の状態セルを読む。

ECS片側タスク停止時の照会継続・タスク復旧と、Aurora writer切替後の再接続を確認する。照会失敗数と復旧結果を記録する。

### 3.8 Webタスク自動増減

構築用希望数0ではタスク・自動増減を起動せず、稼働済み環境を0へ戻す通常変更は拒否する。通常運用は最小2・最大4タスク、ALBRequestCountPerTargetの目標10件／ターゲット／分、増員待機60秒・減員待機300秒、減員有効とする。

対象ECSサービス・ALB・ターゲットグループの一致と、desired_countのignore_changesを確認する。1・5・小数の入力は拒否する。

実Web照会を毎秒1件で継続して4タスクへ増員し、30秒1件へ負荷を下げて2タスクへ減員することを確認する。希望数、実稼働数、正常ターゲット、対象ポリシーの実行履歴を照合する。実稼働数到達後の履歴確定は最大300秒再取得し、増減両方のSuccessfulを合格条件とする。pending、未稼働、増減未発生、別ポリシー・古い・失敗履歴を合格扱いにしない。

希望数は2〜4の範囲で判定し、デプロイ中の実稼働数はdeployment_maximum_percentと分けて確認する。目標10件は増減を確認するための設定値として扱う。

### 3.9 構築・変更管理

Terraform入力、段階構築、ネットワーク・DB・同時実行設定、イメージdigest固定、設定済みSFTPの再利用、対向置換時の設定・実鍵の再取得を確認する。

同じrun内で生成した保存planの適用と、SFTP設定→migration→Web適用の順序、各段階失敗時の停止を確認する。別runの事前planは引き継がず、commit・hash・期限照合や通常リソースの作成・削除・置換ガードは設けない。Lambdaの公開版切替・切戻しでは前後の疎通を確認する。

同時実行枠の確認で新しい上限緩和申請を作らず、既存申請や確保済み枠を正しく判定する。予約枠の有無は実設定と表示・証跡を一致させる。

### 3.10 監視・通知・セキュリティ

監視メトリクス名・dimension・継続期間、ECS通知対象、最終失敗と再試行中の区別、SNS接続、購読Confirmed、代表アラーム発報・メール受信を確認する。ログはJST・レベル・処理段階・結果を記録し、DB成功とS3失敗を区別する。秘密値・生の例外情報を記録しない。

Configの対象資源・記録と個別評価、Security Hubの対象基準・control選択・READY、GuardDutyの基本データソース、Inspectorの検査・検出結果を確認する。構築再開時はstateと所有IDを照合し、管理外設定を変更しない。構成適合、サンプル連携、実検出の各証跡を識別する。

stateバケットのHTTPS強制は既存ポリシーを維持し、重複適用・Sid競合を確認する。S3業務バケットは非現行版だけを30日後に期限切れとし、現行ファイルを維持する。

### 3.11 ログ保持・環境削除・再構築

本体・モック・API・ECS・Aurora・Connectorの全10ロググループについて、稼働中90日保持、skip_destroy=false、専用ログ権限、ログ出力先の事前管理を確認する。

一時削除では一時State空とログ削除、常設削除では常設State空、backend・TLSポリシー・OIDC実行基盤の保持を確認する。常設削除前に一時Stateが空であることを確認する。State外の残存確認は独立したAWS調査として行い、State空だけでアカウント全体の残存なしとは判定しない。

ECRリポジトリとイメージは常設削除のTerraform計画を確認する。独自のイメージ削除ループは使用しない。常設destroyは一時Stateが残る場合に停止し、一時削除後には実行できることを確認する。

現行CLIは旧ログの自動importを行わない。管理外に残る旧ログや旧Connector Stateがある場合は所有範囲を確認し、移行・整理を別作業とする。再構築は現行定義から実施する。

## 4. 実施条件・共通判定

自動試験は依存先を模擬する単体試験、実PostgreSQLを使う結合試験、Terraformの構成試験を区別して実施する。AWS実環境試験は対象commit・stack・プロファイル・設定値を記録し、障害注入後に設定・版・対向サービスを復旧する。

各項目は期待結果と副作用の両方で判定する。タイムアウト、例外、部分失敗、未完了、確認不能を正常終了と読み替えない。構成検査、実動作、通知受信、保持期間の設定確認は、それぞれの証跡に基づいて判定する。

## 5. テスト項目の管理

具体的な試験条件・期待結果は[テスト項目表](テスト項目表.md)に定義する。項目IDを用いて要件・設計との対応と合否判定の基準を識別する。本書は試験の設計を示すものであり、個別項目の実施済み判定やAWS実環境での動作保証を示すものではない。
