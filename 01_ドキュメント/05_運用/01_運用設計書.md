# 運用設計書

## 1. 運用方針

単一の小規模ポートフォリオ環境を対象とする。受付・登録・日次送信・結果反映・監視を自動化し、保守担当者は障害メールを受けて調査・復旧する。定例の人手による日次点検・月次集計は行わない。03:00 JSTに日次完了記録と前日以前の未処理件数を確認し、異常はSNS通知する。通知集約は対象外とする。

日次処理の設計時刻は01:00 JST。Schedulerは既定でDISABLEDとし、定時運用を行う場合に、依存サービス・未処理データ・監視状態を確認して有効化する。

## 2. 監視・通知

CloudWatchの処理・基盤指標、ECS・RDSイベント、GuardDuty・Inspector・Config等の検出結果を集約したSecurity HubのACTIVEかつNEWのHIGH/CRITICAL所見をSNS経由で保守担当者へメール通知する。AWS Budgetsの予算通知はメールで受け、保守担当者が費用内訳を確認する。入力不正は障害通知しない。自動再試行する処理は途中失敗を一律発報せず、DLQ等の最終失敗を監視する。しきい値・保持値は[CloudWatch詳細設計](../03_詳細設計/01_基盤/13_AWS_CloudWatch.md)、通知経路は[SNS詳細設計](../03_詳細設計/01_基盤/15_AWS_SNS.md)を正とする。

監視の運用開始前にSNS購読の確認完了とテストメール受信を確認する。個々の監視項目の発報確認とは区別する。CloudWatch Logsは本体・モック・API・Web/migration・Aurora・Connectorを90日で統一する。Webとmigrationは同一グループ内のstreamで分離する。Auroraの既存グループはTerraform管理へ取り込み、Connectorは専用LoggingRoleで出力する。

## 3. 障害対応

| 障害 | 復旧方針 |
| --- | --- |
| SQS登録失敗 | SDK再試行後も失敗ならAPIで失敗を返す。原因解消後、同じ社員情報を再連携 |
| 非同期登録の継続失敗 | 登録DLQへ隔離。原因を確認して元キューへ戻す。異内容競合を無条件にredriveしない |
| CSV準備失敗 | 割当済みファイル名を基に同名・同内容を保守担当者が手動復元 |
| SFTP送信失敗 | 翌朝に原因解消後、failed/全CSVを同名・同内容で手動再送。自動全件再送なし |
| 結果反映失敗 | 保存済み元結果を使いDBのみ再反映。同期成功確認後だけ保存メッセージを除去 |
| S3配置異常 | 実際の転送結果・元先内容を照合して配置を復旧。DB再反映やCSV再送と分離 |
| Web自動増減 | 1タスク当たり10リクエスト／分を目標に2～4タスクで自動増減。通常の増減は障害として扱わない。最大4タスクでエラーが続く場合や増減に失敗した場合は、ALBリクエスト数・ターゲットの正常性・Scaling activities・DB接続数を確認する |
| ECS/DB障害 | タスク自動復旧・Auroraフェイルオーバー後、接続と業務疎通を確認 |
| DB論理障害・過去時点復元 | 利用可能なバックアップ・CSV・ログから整合回復と再開を個別判断 |

夜間の即時手動対応、ユーザ画面からの保守操作、CSV自動復元機能は設けない。具体操作は[運用手順書](02_運用手順書.md)と[保守ツール詳細設計](../03_詳細設計/03_構築保守/03_保守ツール処理仕様.md)に従う。

## 4. バックアップ・保持・停止再開

Auroraの自動バックアップ保持は7日、取得窓は03:00–03:30 JST、クラスタのメンテナンス窓は日曜03:30–04:00 JST、インスタンスは`portfolio-card-db-1`が日曜04:00–04:30 JST、`portfolio-card-db-2`が日曜05:00–05:30 JST。DB切替・再接続中の一時的なエラーを許容し、無停止を保証しない。通常フェイルオーバーとバックアップ復元を区別する。RPO/RTOの数値保証・過去時点復元後の自動照合・全入力の完全再現は対象外とする。

CSVの現行版は環境存続中保持する。Versioningによる非現行版は非現行化後30日で期限切れにする。現行版を自動削除するライフサイクルは設定しない。CSVは単一Putで扱うため、未完了multipart uploadの自動中断は採用しない。設定変更時は既存の非現行版と変更planを確認する。

常設はVPC・基本経路、state、ECRリポジトリ、OIDC、予算監視、Config証跡保管。一時はアプリ・DB・外部連携・監視・セキュリティ検査設定・Interface Endpoint・対向モック・業務用イメージ。境界は[運用監視基本設計](../02_基本設計/07_運用監視基本設計.md)に従う。

意図的な一時環境削除では未処理を確認・整理し、テストデータをリセットして再投入する。前回データ・処理状態の自動引継ぎを保証しない。これは稼働中障害での受付済み要求保持とは異なる。削除は専用ワークフローの`plan`で内容を確認し、別runの`apply`で実行する。`apply`内で削除planを再生成して適用する。

ログは稼働中90日保持、一時削除時はグループごと削除する。旧設定で残る所有ログも対象とする。常設削除ではConfig証跡も削除し、backend用S3・state・TLSポリシーとOIDC実行基盤は残す。

## 5. 変更・セキュリティ運用

GitHub ActionsとOIDCを入口とし、常設・一時の作成／削除は`plan`で事前確認し、別runの`apply`で実行する。`apply`内ではplanを再生成するため、事前planとの一致は保証しない。初回一時環境の事前planは先行構築範囲に限る。DB互換性を確認し、異常時は正常なタスク定義・Lambda版へ戻す。Secret・鍵は必要時に保守変更として更新し、更新前後の接続を確認する。周期的な自動ローテーションは対象外とする。

Config選択8規則のCOMPLIANTとSecurity Hub FSBP READYを確認する。InspectorのHIGH/CRITICAL所見は利用前に最新イメージで評価し、未解決の場合は対応・利用保留・期限付き例外を判断する。

## 6. 送信成功の確定

`SENT`は成功確定とし、後続の失敗結果ではDB・S3を失敗状態へ戻さない。結果の時刻順序比較は追加しない。DBで反映可否を確認できない場合はS3変更を保留して自動再試行する。`SENT`でもS3配置が未完了の場合は、元の成功結果の再反映で配置を復旧する。DBのみの再反映とS3配置復旧は分けて扱い、CSVを再送しない。
