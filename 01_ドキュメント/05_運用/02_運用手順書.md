# 運用手順書

環境操作は[ワークフロー一覧](../../03_ワークフロー/README.md)の3本。業務保守は認証済みPython環境から既存Lambda・保守モジュールを呼び出す。専用の保守ワークフローは設けない。

## 1. 運用の入口と確認

単一のポートフォリオ環境を対象とする。通常時の人手による日次点検は行わず、CloudWatch／EventBridge／RDSイベントからSNSへ届いた障害通知を起点に調査する。日次処理は01:00 JST、0件の正常終了は通知しない。通知先のSNS購読を確認し、未確認のメール購読を通知可能と扱わない。

Schedulerは既定でDISABLEDとし、定時運用を行う場合に有効化する。GitHub Actionsの同時実行グループで環境操作を直列化する。手動の保守操作はこの排他に含まれないため、実行中のActionsがないことを確認してから行う。操作前に03_Terraform状態確認の最新実行結果と実行中のActionsを確認する。03_Terraform状態確認はState・定義差分の確認であり、アプリの稼働やAWS全体の残存確認は別途行う。


### 保守の共通準備

最新mainを取得したリポジトリのルートで、AWS認証済みのPython環境を使用する。アカウント・リージョンと対象を確認し、利用するAWS SDK等のバージョンは`02_資材/02_temporary/app/requirements.lock`を参照する。GitHub OIDCはActions内の認証であり、ローカル端末へ自動継承されない。以下は同じPythonセッションで実行する。State全体や認証情報は表示・保存しない。

```python
import json, os, subprocess, sys
from pathlib import Path
import boto3
sys.path[:0] = [str(Path("03_ワークフロー/02_資材").resolve()),
               str(Path("02_資材/02_temporary/app").resolve())]
os.environ.setdefault("AWS_DEFAULT_REGION", "ap-northeast-1")
session = boto3.Session()
assert session.region_name == "ap-northeast-1"
account = session.client("sts").get_caller_identity()["Account"]
print("対象アカウント:", account)
# Terraform init済みの一時環境から、公開outputsだけを取得する。
out = {k: v["value"] for k, v in json.loads(subprocess.check_output(
    ["terraform", "-chdir=02_資材/02_temporary/terraform", "output", "-json"], text=True)).items()}
scheduler = session.client("scheduler")
for key in ("scheduler_name", "daily_check_scheduler_name"):
    assert scheduler.get_schedule(Name=out[key], GroupName=out["scheduler_group"])["State"] == "DISABLED"
functions = session.client("lambda")
def invoke(function, payload):
    response = functions.invoke(FunctionName=function, InvocationType="RequestResponse",
                                Payload=json.dumps(payload).encode())
    if response.get("FunctionError"):
        raise RuntimeError("LAMBDA_FUNCTION_ERROR")
    return json.loads(response["Payload"].read())
```

outputs未取得・State空・Scheduler有効の場合は保守処理へ進まない。無効化が必要ならTerraformの`enable_daily_schedule=false`で変更し、両Schedulerと実行中処理を再確認する。`invoke`の戻り値は後述の操作ごとの基準で判定する。

保守完了後はDB・S3・転送結果の整合と実行中処理の終了を確認し、定時運用を再開する場合はTerraformで`enable_daily_schedule=true`へ戻す。01:00の日次処理と03:00の完了確認の両Schedulerが有効であることを確認する。

結果再反映では、上の準備に続けて以下を実行する。`message_id`は調査で特定した実際の値へ置き換える。

```python
from tools.maintenance.replay_result import replay
kind = "delivery"  # Lambda最終失敗レコードの場合はexecution
message_id = "対象のMessageId"
expected = dict(account=account, region=session.region_name,
                connector=out["connector_id"], bucket=out["exchange_bucket"])
result = replay(session.client("sqs"), functions, out[kind + "_queue_url"],
                kind, message_id, out["result_function"], expected)
```

`replay`が応答検証と成功後のSQS削除を行う。S3配置復旧は5節に従い別途確認する。

## 2. 障害時の確認順序

1. 通知のアラーム名・発生時刻・対象関数／キュー／ファイルを確認する。
2. 該当LambdaのCloudWatch LogsでJST時刻、process、stage、error_code、filename／request_idを確認する。DB更新とS3配置変更は別々に判定する。
3. Transfer Familyの転送実績とS3のtransfer/・failed/・success/を確認する。ファイルの残存だけで未送信と判断しない。
4. DB状態は社員番号でWeb照会する。本文・認証情報・秘密鍵をログや作業記録へ転記しない。
5. 原因解消後、以下の復旧操作を選び、DB・S3・転送結果の整合を確認して記録する。

| 異常 | 復旧操作・完了条件 |
| --- | --- |
| API入力不正（400） | ID管理側で修正して再連携。SQS未登録が正常 |
| APIのSQS登録失敗（500） | 原因解消後に同じ社員情報を再連携 |
| DB登録の継続失敗／異内容の社員番号重複 | registration DLQの対象を確認し、入力または基盤を是正。同内容再連携では重複行を作らない |
| CSV準備失敗 | 割当済みsend_filenameに対応する行をDBから抽出し、[DB・ファイル詳細設計](../03_詳細設計/02_アプリ/02_DB・ファイル詳細設計.md)の列・文字コード・改行・SHA-256メタデータで同名CSVを復旧。transfer/への保存完了を確認し、次回日次処理で送信 |
| SFTP送信失敗 | 対向・接続を復旧し、failed/全件再送。SENTとsuccess/への移動を確認 |
| 結果反映の最終失敗 | 保存された元結果を使いDBのみ再反映。S3配置の復旧は別途実施 |
| ECSタスク障害 | 自動再作成、正常ターゲット数、Web照会を確認 |
| Aurora writer障害 | フェイルオーバー完了と接続再確立、Web／後続処理の成功を確認 |

## 3. SFTP再送

1節の共通準備後、既存の再送Lambdaを同期Invokeする。

1. Schedulerを停止し、実行中の転送・結果反映がないことを確認する。
2. 転送結果と配置を照合する。成功済みCSVがfailed/に残っていれば先にsuccess/へ復旧する。
3. `invoke(out["resend_function"], {"mode":"resend_failed", "placement_checked":True})`を実行する。戻り値`ok=true / failed=0 / not_sent=0`を確認する。再送LambdaはDBを参照せずfailed/全CSVを送信する。
4. Lambdaの正常応答は転送要求の受付を示す。最終成功はTransfer実績、DB SENT、success/配置で確認する。
5. 再失敗時はfailed/を保持して原因を調査する。自動の全件再送は行わない。

## 4. 結果の再反映

| 保存先 | queue_kind | 内容 |
| --- | --- | --- |
| result delivery DLQ | delivery | EventBridgeが配信できなかった元イベント |
| result execution DLQ | execution | Lambda最終失敗レコードのrequestPayload |

1. Scheduler停止・原因解消を確認する。
2. SQSに保存された対象のMessageIdを確認する。内容に含まれるaccount・region・connector・bucket・filenameが対象環境と一致することを確認する。
3. 共通準備で読み込んだ`replay`へ、対象キュー・kind・MessageIdを指定する。1節の結果再反映例に従う。
4. 保守ツールは既存の結果反映Lambdaを同期呼出しし、DBのみを更新する。`ok=true / db=OK / s3=SKIPPED`の一致後にだけメッセージを削除する。関数の起動受付だけでは削除しない。
5. Webで対象社員の状態と転送結果の一致を確認する。失敗したメッセージは残して再調査する。

## 5. S3配置の復旧

| 実際の転送結果 | 正しい配置 |
| --- | --- |
| 成功 | success/ |
| 失敗 | failed/ |

元・移動先の内容とSHA-256を確認する。同一内容ならコピー確認後に元を削除する。移動先だけに同一内容があれば配置済みとして扱う。両方なし・異内容は上書きせず調査する。転送成功後にtransfer/へ残ったファイルは次回日次処理までに復旧する。

DB更新だけ失敗した場合はDB再反映のみ、S3だけ失敗した場合は配置復旧のみ、両方失敗した場合は両方を実施する。未完了CSVは再処理完了まで保持する。

## 6. 変更・切り戻し

作成・更新は02または04、削除は05または03をmainで手動実行する。先にmode=`plan`のログで変更内容を確認し、別runでmode=`apply`を実行する。applyではplanを再生成して適用するため、事前planとの一致は保証しない。初回一時planは先行構築範囲に限る。詳細は[現行仕様](../../03_ワークフロー/README.md)を参照。

Webは直前の正常タスク定義とイメージ、Lambdaは直前の正常な公開版へ戻す。DBスキーマと入力の互換性を確認し、切り戻し後にWeb・業務疎通を確認する。Terraform変更は内容を確認した修正planで戻す。

DB論理障害の個別修正・過去時点復元は影響調査後に判断する。CSV・ログ・バックアップと照合し、整合回復後に再開する。消費済みSQSや全入力の完全復元、自動照合は保証範囲に含めない。

## 7. 停止・再構築

停止前に受付・Schedulerを止め、実行中処理とキュー残存を確認する。ポートフォリオのテストデータは再構築時に再投入する。

05で本体・対向モック・DB・S3データ・CloudWatch Logsを削除する。ログは稼働中90日保持し、環境削除後は保持しない。旧設定の所有ログも削除する。常設も不要なら03を実行する。常設削除ではConfig証跡・ECRイメージも削除するが、backend・state・TLSポリシーとOIDC実行基盤は残す。KMSのPendingDeletionは削除予約として記録する。

GuardDuty／Inspector／Config recorder／Security Hubは本環境が新規に所有した設定だけを停止・削除する。既存の共有設定があるアカウントでは無断で採用・停止しない。Config証跡バケットの保持と継続記録の停止を区別する。

再開時は構築、SFTP設定、DB migration、Web起動、監視とSNS購読を確認して疎通試験する。費用抑制の停止期間は24時間365日稼働の実績に含めない。

## 8. Security Hub基準がINCOMPLETEの場合

1. 通知・確認時点のStandardsStatusと理由を確認する。Config記録成功や一部controlの適合だけで基準全体READYと判断しない。
2. NO_AVAILABLE_CONFIGURATION_RECORDERの場合、Configの対象4種別、記録成功、既存8規則の適合を確認する。前提不足があれば先に是正し、基準の再作成で隠さない。
3. AWS Config・Security Hubのコンソールまたは読取専用APIで記録状態、基準のステータス、選択したcontrolを確認する。読み取りによる確認中に基準・規則の作成や削除は行わない。
4. `StandardsStatus=READY`とConfigの記録・8規則の評価をそれぞれ確認する。ステータスがINCOMPLETEのままなら原因を調査し、READYとみなさない。
5. 想定外状態・設定変化・権限エラー・タイムアウトは未解決として停止する。既存基準/規則を無効化・削除したり、同じ要求を連続起動したりしない。原因を調べ、必要な変更は影響を確認して判断する。

RDS個別評価不足はAWS Configで記録対象・評価状態・適用規則を確認する。必要な再評価の前に記録が有効であることを確認し、管理外のルールを変更しない。Security Hub READYでもInspectorの未解決脆弱性は別途対応する。

## 9. InspectorのHIGH/CRITICALと修正版未提供時

1. findingArn、CVE、対象digest、fixAvailable、fixedInVersion、exploitAvailableを確認する。古い非稼働imageの所見と稼働imageを区別する。
2. InspectorとECSタスク定義から、findingのimage digestと稼働イメージのdigestを照合する。非稼働イメージの所見と現在稼働するコンテナの所見を区別する。
3. 配布元の安定版セキュリティ情報を実package/source versionと照合する。上流バージョン番号だけで影響なし・誤検知と判定しない。
4. 互換性のある修正版がある場合は再ビルド・CI・再検査・変更plan確認後に更新し、業務疎通と対象所見の解消を確認する。
5. 未提供ならアプリ利用経路・既存制限・残る不確実性を整理する。例外の提案と受容を区別し、期限付き継続か利用保留かを判断する。
6. 期限または利用再開前、修正版提供・影響変更・悪用情報・関連通知を契機に見直す。自動監視や自動停止がない場合は、その点も明記する。

過去の脆弱性診断結果を現在の安全性の根拠として再利用しない。利用前に最新イメージで再検査し、未解決のHIGH/CRITICAL所見は対応または期限・根拠を定めた例外承認が必要となる。

## 10. CloudWatchログの保持確認

対象10グループは[CloudWatch詳細設計](../03_詳細設計/01_基盤/13_AWS_CloudWatch.md)の一覧を正とし、稼働中retentionInDays=90、一時削除時skip_destroy=falseとする。旧logs-preserve操作は使用しない。旧設定でState管理外に残ったログは自動再取込みしない。必要なら所有範囲を確認して別途整理する。

## 11. 成功確定後の失敗結果

SENTを確認済みのファイルは、古い失敗結果の再配信でも失敗へ戻さない。ignored_after_success=true / s3=SKIPPEDは正常な省略である。DBの更新を省略したことを理由にCSVを再送しない。成功結果の再配信は省略せず、未完了のsuccess/配置を復旧する。

DBに接続できない場合はS3変更も保留される。最終失敗の復旧では原因解消後、保存元結果のDBのみ再反映を確認し、S3配置を別途確認する。DBのみの再反映でファイルも移動済みとは判断しない。成功の元結果を通常入力で再反映すれば、CSV再送なしで成功配置を修復できる。


## 12. 日次未実行・未処理

03:00 JSTに当日の日次完了記録と前日以前の未処理件数を自動確認する。翌朝は共通準備後、両Schedulerが無効であることを確認し、`invoke(out["batch_function"], {"schema_version":1,"mode":"check_daily"})`で完了確認を行う。`ok=true`を確認する。日次再実行が必要なら`invoke(out["batch_function"], {"schema_version":1,"mode":"daily"})`を呼び、`overall=OK`と後続の転送結果を確認する。未実行とCSV準備途中失敗、転送失敗、結果未反映を分け、成功済みCSVを再送しない。

## 13. Webタスクの自動増減

通常は希望数2～4の範囲で自動管理する。タスク数が増減しただけでは障害としない。ALB 5xx・不健全ターゲット・ECS起動失敗の通知が続く場合、RequestCountPerTarget、希望数・稼働数・保留数、Scaling activitiesの理由、DB接続数を確認する。

最大4でも障害が続く場合は、先にアプリ・DB・依存先と流量を調査する。上限を無条件に引き上げず、必要な変更は設計・費用・接続数の影響を確認してplan/applyする。停止目的で希望数だけを0へ変更しない。通常の停止は7節の一時環境削除を使用する。
