# カード発行業者モック 設計・仕様

## 1. 目的・構成

カード発行業者の代わりに、Transfer Family SFTP Connectorから入館証発行依頼ファイルを受領する。Public SubnetのEC2 1台とOpenSSH SFTPで構成する。

| 項目 | 設計 |
| --- | --- |
| 通信 | Connector（Service managed egress）→ EC2のElastic IP、TCP 22 |
| 認証 | `badge_sftp`専用ユーザの公開鍵認証 |
| 接続元 | 使用するConnectorの送信元IPv4アドレスだけを許可 |
| ホスト検証 | 管理経路で確認したEC2のホスト公開鍵をConnectorへ登録 |
| 受領先 | SFTP上の`/inbox`、OS上の`/srv/sftp/badge_sftp/inbox` |
| 再送 | 同名ファイルを上書きして全体を置き換える。同名・同内容での再送を想定 |
| 管理 | Systems Manager Session Manager。管理用SSHは公開しない |
| 対象外 | 自動取込、CSV業務検証、カード発行、結果API、冗長化 |

基本方式は[外部連携方式設計](../../02_基本設計/02_外部連携方式設計.md)に従う。本書は構築仕様であり、AWS配置・試験完了を示さない。

## 2. 受領動作・データ

1. OpenSSHが公開鍵認証を行い、専用ユーザの操作をchroot内のSFTPに限定する。
2. Connectorが指定した名前で`/inbox`へ書き込む。受領側ではファイル名変更・別パスへの移動を行わない。
3. OpenSSHはファイル操作に応答する。転送完了の業務側判定・DB反映・S3配置変更は本システムがConnectorイベントに基づいて行う。

| 観点 | 動作・確認範囲 |
| --- | --- |
| ファイル名 | 本システムが作成した秒までのJST日時を含む名前を保持。例：`request_20261016010000_a1b2c3d4.csv`。例を受領側の名前検証には使用しない |
| 内容 | 社員番号・氏名・所属会社名・入館証番号の4項目を含むCSVを想定。受領側はバイト列として保存し、解析しない |
| CSV物理形式 | 本システムのCSV詳細設計に従う。受領側の構築にヘッダー・改行・項目順の確定は不要 |
| 正常確認 | 送信元S3とEC2受領ファイルのサイズ・SHA-256が一致し、4項目の値が保持されている |
| 再送 | 既存ファイルを上書きし、送信元との一致を再確認。履歴ファイルや二重処理判定DBは作らない |
| 中断 | 部分ファイルが残る場合がある。ファイルの存在だけで送信成功と判定しない |
| 受領後 | 自動削除しない。テストデータは環境削除時にEBSとともに削除 |

作成時の名前で直接受領し、`.tmp`送信・送信後renameは行わない。自動取込がないため、実対向に求める転送途中の取込防止・二重業務処理防止はモックの実装・検証範囲に含めない。

## 3. OS・SFTP設定

### 3.1 ユーザ・ディレクトリ

| OSパス／設定 | 所有者 | 権限・内容 |
| --- | --- | --- |
| `badge_sftp` | 専用ユーザ・専用グループ | sudo権限なし、パスワード認証なし。アカウント有効期限なし |
| ユーザのホーム | — | chroot内の`/inbox`。シェルは`/bin/bash`だが、接続時は下記`ForceCommand`でSFTPに限定 |
| `/srv`、`/srv/sftp` | `root:root` | `0755`、非rootから書込不可 |
| `/srv/sftp/badge_sftp` | `root:root` | `0755`、chrootのルート。専用ユーザへ書込権限を付けない |
| `/srv/sftp/badge_sftp/inbox` | `badge_sftp:badge_sftp` | `0700`、ファイル受領先 |
| `/etc/ssh/authorized_keys` | `root:root` | `0755` |
| `/etc/ssh/authorized_keys/badge_sftp` | `root:root` | `0644`、専用ユーザの公開鍵1個のみ。秘密鍵は配置しない |
| `/etc/ssh/ssh_host_ecdsa_key` | `root:root` | `0600`、EC2で生成するホスト秘密鍵 |
| 受領ファイル | `badge_sftp:badge_sftp` | umask `0077`。新規ファイルは通常`0600` |

chrootの全親ディレクトリはroot所有・他者書込不可とする。専用ユーザは公開鍵でログイン可能なアカウント状態にし、PAMやアカウント失効で鍵認証まで拒否しない。パスワードログインはsshd設定で禁止する。

### 3.2 sshd設定

既存のSubsystem定義を以下へ置き換え、設定の重複を避ける。Matchブロックはグローバル設定の後へ配置し、後続のグローバル設定を巻き込まない。

```text
Port 22
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
HostKey /etc/ssh/ssh_host_ecdsa_key
Subsystem sftp internal-sftp

Match User badge_sftp
    AuthenticationMethods publickey
    AuthorizedKeysFile /etc/ssh/authorized_keys/%u
    ChrootDirectory /srv/sftp/%u
    ForceCommand internal-sftp -d /inbox -u 0077
    DisableForwarding yes
    PermitTTY no
    PermitTunnel no
    PermitUserRC no
    X11Forwarding no
```

OpenSSHはOS提供パッケージを使用する。構成適用はcloud-init／構成スクリプトに記述し、`sshd -t`が成功した場合だけ反映する。SSM Agentとsshdを自動起動する。sshdの接続・認証ログはOSのjournaldで確認する。ファイル別の転送結果は本システムのConnectorイベント、内容一致は受領ファイルで確認するため、chroot内のファイル操作ログ基盤は追加しない。受領ファイル内容・秘密鍵はログ出力しない。

## 4. AWSパラメータ・通信

以下はモック用の採用値。AMI ID・Subnet ID・IP・ARN・公開鍵は構築結果または入力で置き換える。

| パラメータ | 意味 | 既定値 | 設定値 | 理由 |
| --- | --- | --- | --- | --- |
| `region` | リージョン | Provider設定による | `ap-northeast-1` | 本システムと同一環境 |
| EC2台数 | モック台数 | 設計値 | 1 | 冗長化は対象外 |
| `ami` | OS | 指定必須 | Amazon Linux 2023 x86_64。公式SSMパラメータ`/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64`で取得したID | OpenSSH・SSM Agentを使用。採用IDをplan・構築記録に残す |
| `instance_type` | EC2サイズ | 指定必須 | `t3.micro` | 少量ファイルの受領用途 |
| `subnet_id` | 配置先 | 指定必須 | 既存Public Subnetの1つ | IGW経由で公開SFTPを提供 |
| `associate_public_ip_address` | 自動Public IP | Subnet等による | `false`、別途Elastic IPを関連付け | 接続先IPv4を固定 |
| EIP `domain` | EIP用途 | `vpc` | `vpc`、1個 | EC2停止・起動で接続先を維持 |
| `root_block_device.volume_type` | EBS種別 | AMI等による | `gp3` | 小規模受領用途 |
| `root_block_device.volume_size` | EBS容量 | AMIによる | 8 GiB。採用AMIの最小容量が大きい場合はその最小容量 | OSと少量のテストデータ |
| `root_block_device.encrypted` | 保存暗号化 | アカウント等による | `true`、AWS管理鍵 | 保存データ保護 |
| `root_block_device.delete_on_termination` | 削除時のEBS | AMI等による | `true` | 再構築時にデータをリセット |
| `metadata_options.http_tokens` | IMDS | アカウント等による | `required` | IMDSv2を必須化 |
| `key_name` | 管理用SSH鍵 | 未設定 | 未設定 | 管理はSSM経由 |
| `iam_instance_profile` | EC2実行権限 | 未設定 | `AmazonSSMManagedInstanceCore`相当のSSM用ロール | Session Manager・構成反映 |
| SG ingress | TCP 22受信 | なし | Connectorの各送信元IPv4 `/32` | 不特定送信元からのSSHを拒否 |
| SG egress | HTTPS送信 | 全許可 | TCP 443、`0.0.0.0/0` | SSM接続・OSパッケージ取得。専用Endpointを増設しない |

Public Subnetには`0.0.0.0/0 → IGW`の経路を持たせる。VPC DNSを有効にし、標準NACLの戻り通信を許可する。SSM用に`ssm.ap-northeast-1.amazonaws.com`、`ssmmessages.ap-northeast-1.amazonaws.com`へHTTPSで到達可能とする。モック用NAT Gateway・SSM専用VPC Endpointは追加しない。

Terraformの一時環境にEC2・EIP・SG・IAMを含める。EIPも一時環境削除時に解放する。モックには本システムのDB・S3・Secret取得権限を与えない。

## 5. 鍵・Connectorへの受渡し

### 5.1 鍵の管理

| 鍵 | 作成・保存 | 公開部分の受渡し |
| --- | --- | --- |
| SFTPユーザ鍵 | 構築処理でRSA 3072 bit、パスフレーズなし・PEM形式として生成。秘密鍵はSecrets Managerへ保存 | 公開鍵をEC2の`authorized_keys`へ設定 |
| サーバホスト鍵 | EC2でECDSA nistp256を生成。秘密鍵は当該EC2にだけ保存 | SSM管理経路から確認した公開鍵を`TrustedHostKeys`へ設定 |

ユーザ秘密鍵の生成・Secret値の登録はTerraformの外側の構築処理で行う。TerraformはSecretの入れ物・ARNを管理し、`tls_private_key`や`secret_string`、user-dataへ秘密鍵の実値を持たせない。生成処理は値を標準出力・Actions成果物へ残さず、一時ファイルを処理終了時に削除する。EC2へ渡すのは公開鍵のみとする。

Secret名は`portfolio/mock/card-vendor/sftp`とし、値は次のJSON構造とする。`PrivateKey`は改行を含むPEM秘密鍵文字列で、`Password`は指定しない。

```json
{
  "Username": "badge_sftp",
  "PrivateKey": "<PEM形式の秘密鍵文字列>"
}
```

### 5.2 接続設定

| 本システム側の設定 | 値・取得元 |
| --- | --- |
| Connector `Url` | `sftp://<EC2のElastic IP>:22` |
| `EgressType` | `SERVICE_MANAGED` |
| `SftpConfig.UserSecretId` | 上記SecretのARN |
| `SftpConfig.TrustedHostKeys` | `ecdsa-sha2-nistp256 <Base64公開鍵>`。ホスト名・コメントを除く |
| `SftpConfig.MaxConcurrentConnections` | 1。少量転送のため並列度を上げない |
| `StartFileTransfer.RemoteDirectoryPath` | `/inbox`。OS上の絶対パスを渡さない |
| EC2 SGへの入力 | `DescribeConnector`の`ServiceManagedEgressIpAddresses`全件を各`/32`にして設定 |

Connectorアクセスロールには当該Secretへの`secretsmanager:GetSecretValue`を付与する。SecretはSecrets ManagerのAWS管理鍵で暗号化する。S3・転送イベントに関する本システム側の権限は本システムの詳細設計で管理する。

構築の依存関係は、EC2・鍵・Secret準備 → 接続先とホスト公開鍵を受け渡してConnector作成 → 割当済み送信元IPをSGへ反映 → 接続試験とする。SGを全開放する中間状態は作らない。EC2再構築時はホスト鍵を再取得し、Connectorを更新する。Connector再作成時はSGの送信元IPも更新する。

## 6. 実装の確認条件

| 条件 | 期待結果 |
| --- | --- |
| 正常送信 | `/inbox`へ元の名前で保存、S3とサイズ・SHA-256一致 |
| 同名・同内容で再送 | 成功し、受領後も元データと一致 |
| 不正なユーザ秘密鍵 | 認証失敗 |
| ホスト公開鍵不一致 | Connector側で検証失敗。検証を無効化して通さない |
| 許可外の送信元 | TCP 22へ接続不可 |
| 専用ユーザのシェル・ポート転送 | 使用不可。chroot外のファイルにアクセス不可 |
| EC2停止・sshd停止・受領先書込不可 | 本システムで送信失敗を検知。部分ファイルの存在を成功根拠にしない |
| 復旧後に同じファイルを手動再送 | ファイル全体が一致。本システムで`SENT`・S3 `success/`への反映 |
| 管理経路 | 管理用SSHを許可せず、Session Managerから受領内容を確認可能 |
