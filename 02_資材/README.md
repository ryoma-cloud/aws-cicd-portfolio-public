# 資材作成方針

AWS基盤を定義するTerraformと、入館証発行管理のアプリケーションを配置する。

## 1. 作成方針

- 詳細設計に基づき、基盤構成、業務処理、Web画面およびDBマイグレーションを実装する。
- AWS環境の構成はTerraformの定義を正本とし、リソース間の依存関係に基づく構築順序はTerraformに任せる。
- 常設基盤と一時環境を分離し、作成は常設→一時、削除は一時→常設の順序とする。
- 業務処理はアプリケーション資材、構築・削除・状態確認・保守はワークフロー資材で管理し、役割を分離する。
- 資材の変更時は、ファイル同士の参照関係やコンテナに含める資材への影響を確認し、設計書とテスト資料の整合を保つ。

| ディレクトリ | 役割 |

| `01_persistent/` | VPC、サブネット、ECR、ログ、予算、Config証跡保管などの常設基盤 |

## 3. AWS環境の構成管理

AWSリソースの作成・変更・削除はTerraformで管理し、GitHub Actionsから実行する。ネットワークなどの常設基盤と、アプリケーション・DBなどの一時環境を分離して管理する。

監視・セキュリティ・外部接続もTerraformで設定する。サービスの利用開始や接続先の準備が必要な場合は、それらを先に完了してから関連設定を適用する。

通知先のメールアドレスはGitHub Actionsの設定から渡す。メール通知の購読確認は受信者が行う。

## 4. 構築作業の依存関係と自動化

構築作業には、前の作業が完了しないと次へ進めない依存関係がある。例えば、SFTP接続先の作成・初期設定が終わってから接続相手を確認するための鍵を取得し、その鍵を接続設定へ反映する。また、新しいWebアプリケーションの反映前には、DBのテーブルなどの準備を完了させる必要がある。

AWSリソース同士の依存関係はTerraformで管理できる。一方、構築にはコンテナイメージの作成・登録、サーバの初期設定、DBのテーブル作成など、リソースを用意するだけでは完了しない作業もある。

Terraformから外部コマンドを呼び出す方法もあるが、本システムでは、これらの作業とTerraformの実行をPythonで取りまとめる。作業の実行、結果の確認、失敗時の停止をまとめて扱い、前の作業が正常に完了してから次へ進む手順を明確にするためである。リソース間の依存関係で解決できる順序はTerraformに任せ、Pythonは構築に必要な補助作業と、その前後の実行順序を担当する。主な対象は以下とする。

- アプリケーションを配布用にまとめ、コンテナイメージを作成・登録する。
- SFTP接続先を初期設定し、接続相手を確認するための鍵を取得・設定する。
- DBにテーブルなどを作成・更新してから、新しいWebアプリケーションを反映する。
- 接続に必要な秘密鍵やパスワードを生成・登録する。

各作業は、接続先やDBの準備が整ってから次の処理へ進めるよう、実行順序を制御する。秘密情報の保存先とアクセス権限はTerraformで管理する。

## 5. 管理情報の保護

Terraformが管理するリソースの情報を記録したStateは、専用のS3に保存する。この保存先と、GitHub ActionsがAWSへ接続するための認証基盤は、環境削除後も保持する。

State保存先には暗号化されていない通信を拒否する設定を適用し、既存のほかの設定を維持する。この保護設定は構築処理で適用するため、Terraformが表示する変更予定には含まれない。

過去の構成の管理情報が残っている場合は、削除や移行を自動で進めず、管理情報とAWS上のリソースを確認してから対応する。
