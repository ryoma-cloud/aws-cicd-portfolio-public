# ワークフロー概要

## 1. 3つのワークフロー

本書は、3つのワークフローの概要と処理の流れを示す。CIテストは第2章、環境操作の共通事項は第3章、選択した環境・操作に応じた処理は第4〜7章、Terraform状態確認は第8章に記載する。

①〜③は各ワークフローの識別番号であり、GitHub Actionsの表示名およびYAMLファイルの番号01〜03に対応する。

| 本書の番号 | GitHub Actions表示名 | 定義ファイル | 概要 |
| --- | --- | --- | --- |
| ① | 01_CIテスト | [01_ci.yml](../../.github/workflows/01_ci.yml) | Python・Terraformとワークフローを検査 |
| ② | 02_環境操作 | [02_environment.yml](../../.github/workflows/02_environment.yml) | 常設環境・一時環境の作成・変更・削除を実施 |
| ③ | 03_Terraform状態確認 | [03_aws-status.yml](../../.github/workflows/03_aws-status.yml) | 常設環境・一時環境の管理対象と構成差分を確認 |

②・③はmainブランチから個別に手動起動する。②では次の3項目を選択する。

| 入力項目 | 選択値 | 意味 |
| --- | --- | --- |
| 対象環境（stack） | persistent／temporary | 常設環境／一時環境 |
| 操作（operation） | apply／destroy | 作成・変更／削除 |
| 実行区分（mode） | plan／apply | 計画の確認／操作の実行 |

operationの`apply`は作成・変更を示し、modeの`apply`は選択した操作の実行を示す。例えば、`temporary / destroy / plan`は一時環境の削除計画を表示し、`temporary / destroy / apply`は一時環境を削除する。既定値は`temporary / apply / plan`とする。

環境の作成は「常設環境 → 一時環境」、削除は「一時環境 → 常設環境」の順に行う。一時環境が常設環境のリソースを利用するためである。1回の起動では選択した環境・操作のみを実行し、環境間の自動連携は行わない。操作者は各実行の完了を確認してから次の操作を起動する。

## 2. ワークフロー①：CIテスト

AWS反映前に、Python・Terraformの基本的な不備を検出する。[01_ci.yml](../../.github/workflows/01_ci.yml)の構成と処理順序を以下に示す。

| 番号 | 項目 | 処理内容 |
| --- | --- | --- |
| 1 | 起動条件定義 | 手動操作、PR、対象パスのmainへのpushで起動する。 |
| 2 | 権限設定 | GitHubが、ジョブ用の認証トークンにリポジトリの読取権限を付与する。 |
| 3 | Linux実行環境の起動 | Python・Terraformの検証コマンドを実行するため、GitHubが提供する基盤上にUbuntuの一時的な仮想マシン（ランナー）を起動する。 |
| 4 | コード取得 | GitHub上のリポジトリから、今回の検証対象となるコード・設定ファイルを番号3のUbuntuランナー内へコピーし、検証コマンドが読み込める状態にする（actions/checkout）。 |
| 5 | Python導入 | Python 3.13を導入する。 |
| 6 | Python構文確認 | Pythonファイルの構文エラーを検査する。 |
| 7 | 模擬実行用ライブラリ導入 | ワークフロー検証に使用するPyYAMLを導入する。 |
| 8 | ワークフロー模擬実行検証 | AWSへ接続せず、入力の受渡し、処理順序、失敗時停止を検証する。 |
| 9 | Terraform導入 | Terraform 1.16.2を導入する。 |
| 10 | Terraform書式確認 | 常設環境・一時環境のコードの書式を検査する。 |
| 11 | 検証用ZIP作成 | Terraformの検証に必要な空ZIPを6つ作成する。 |
| 12 | Terraform定義検証 | 常設環境・一時環境を初期化し、定義の整合性を検査する。 |
| 13 | 結果出力 | 各検査の実行ログと、CI全体の成功・失敗をGitHub Actionsの実行画面に表示する。検査で不備を検出した場合は、対象ファイルやエラー内容をログに出力する。 |
| 14 | 結果確認 | 操作者は実行結果を確認する。成功の場合は、Python構文・ワークフロー模擬実行・Terraform書式・Terraform定義の検査に合格したと判断する。失敗の場合は、ログから原因を特定し、コード・設定等を修正して再実行する。 |

Python構文確認後に、ワークフローの入力分岐・処理順序・失敗時の停止を模擬CLIで検証する。AWS認証や実際のAWS操作は行わない。

## 3. ワークフロー②：環境操作の共通事項

環境操作の共通処理を本章にて示し、対象環境・操作ごとの処理は第4〜7章に示す。

### 3.1 起動条件・設定・認証

| 番号 | 項目 | 処理内容 |
| --- | --- | --- |
| 1 | 起動条件定義 | 手動操作で起動し、mainブランチでのみ処理を実行する。起動時に、対象環境（stack）、操作（operation）、実行区分（mode）を選択する。 |
| 2 | 権限設定 | GitHubが、ジョブ用の認証トークンにリポジトリの読取権限を付与し、ジョブによるAWS認証用のOIDCトークンの取得を許可する。 |
| 3 | 同時実行制御 | ②・③を共通の実行グループで管理する。他のワークフローが実行中の場合は待機し、環境操作と状態確認の競合を防止する。 |
| 4 | Linux実行環境の起動 | AWSの操作に必要なコマンドを実行するため、GitHubが提供する基盤上にUbuntuの一時的な仮想マシン（ランナー）を起動する。 |
| 5 | コード取得 | GitHub上のリポジトリから、操作に使用するコード・設定ファイルを番号4のUbuntuランナー内へコピーする（actions/checkout）。 |
| 6 | Python導入 | Python 3.13を導入する。 |
| 7 | Terraform導入 | Terraform 1.16.2を導入する。 |
| 8 | Python実行設定 | AWS操作・SFTP鍵生成に必要なライブラリを導入し、補助プログラムのモジュール検索先を設定する。 |
| 9 | AWS認証 | GitHubのOIDCトークンを使用して指定のIAMロールを引き受け、AWS操作に必要な一時認証情報を取得する。 |

### 3.2 失敗時の対応

環境の作成・変更・削除が途中で失敗した場合は、後続の処理を停止する。反映済みの構成およびDB更新の自動切り戻しは行わない。操作者は実行結果と現在の状態を確認し、原因を解消したうえで再実行する。

## 4. 環境操作：常設環境作成・変更

一時環境の作成・更新に必要な共通基盤として、VPC・ECR・IAM等を整備する。

第4〜8章のプログラムファイルは、原則として`03_ワークフロー/02_資材/`からの相対パスで記載する。別途明記するパスは、`.github/`が配置される構成のルートから記載する。共通の起動準備・AWS認証は第3章に従う。

| 番号 | 実施事項 | 処理内容 | プログラムファイル | 使用する関数 |
| --- | --- | --- | --- | --- |
| 1 | 操作内容の判定 | 対象環境・操作・実行区分を解釈し、常設環境の作成・変更処理を選択する。 | `tools/environment.py` | `main`、`execute` |
| 2 | 管理情報への接続 | 常設環境のTerraformを初期化し、S3に保存した管理情報へ接続する。 | `tools/environment.py` | `initialize` |
| 3 | 管理対象の確認 | 常設環境の管理対象リソースを取得する。取得に失敗した場合は停止する。 | `tools/environment.py` | `state_list` |
| 4 | 通知先の設定 | 予算通知先をTerraformへ渡す。`apply`では通知先を必須とし、未設定の場合は停止する。 | `tools/environment.py` | `persistent_inputs` |
| 5 | 管理情報への通信の保護 | `apply`の場合、管理情報用S3への暗号化されていない通信を拒否する。既存の他のポリシー設定は維持する。 | `tools/environment.py` | `persistent_inputs` |
| 6 | 変更計画の作成 | 現在の構成と定義を比較し、必要な作成・変更・削除の計画を作成する。`plan`の場合は計画を表示して終了する。 | `tools/environment.py` | `plan`、`apply`、`tf` |
| 7 | 常設環境への反映 | `apply`の場合、同じ実行内で作成した計画を適用し、共通基盤を整備する。 | `tools/environment.py` | `apply`、`tf` |

リソースの具体的な構成は`02_資材/01_persistent`のTerraform定義に従う。リソース間の作成順序はTerraformが制御する。

管理情報用S3の通信制限はAWS CLIで設定するため、Terraformの変更計画には含まれない。

`apply`の正常終了時は、常設環境への構成反映が完了した状態とする。一時環境の作成・変更は別途実施する。

## 5. 環境操作：常設環境削除

システムの利用終了時に、常設環境の管理対象リソースを削除する。一時環境が利用する共通基盤の先行削除を防止するため、一時環境の削除完了後に実施する。

| 番号 | 実施事項 | 処理内容 | プログラムファイル | 使用する関数 |
| --- | --- | --- | --- | --- |
| 1 | 操作内容の判定 | 対象環境・操作・実行区分を解釈し、常設環境の削除処理を選択する。 | `tools/environment.py` | `main`、`execute` |
| 2 | 管理情報への接続 | 常設環境のTerraformを初期化し、S3に保存した管理情報へ接続する。 | `tools/environment.py` | `initialize` |
| 3 | 削除対象の確認 | 常設環境の管理対象を取得する。対象が存在しない場合は終了する。 | `tools/environment.py` | `state_list` |
| 4 | 管理情報の保護条件の確認 | 管理情報用S3の通信制限が旧Stateに登録されている場合は、誤って削除しないよう処理を停止する。 | `tools/environment.py` | `execute` |
| 5 | 一時環境の削除完了確認 | `apply`の場合、一時環境の管理対象が残っていないことを確認する。残存または取得失敗の場合は停止する。 | `tools/environment.py` | `execute`、`initialize`、`state_list` |
| 6 | 削除計画の作成・表示 | 常設環境の削除計画を作成し、対象を表示する。`plan`の場合は表示して終了する。 | `tools/environment.py` | `execute`、`tf` |
| 7 | 常設環境の削除 | `apply`の場合、同じ実行内で作成した削除計画を適用する。 | `tools/environment.py` | `execute`、`tf` |

リソース間の削除順序はTerraformが制御する。一時環境の残存確認は`apply`で実施し、`plan`では実施しない。

`apply`の正常終了時は、常設環境の管理対象リソースの削除が完了した状態とする。管理情報用S3、Stateファイル、S3の通信制限およびOIDC認証基盤は保持する。

## 6. 環境操作：一時環境作成・変更

受付・ファイル連携・DB・Web画面等の機能を提供する環境を整備する。ファイル連携先の設定およびDB更新を、新しいWebアプリケーションの反映に先行して実施する。

前提として、常設環境の作成が完了していること。

| 番号 | 実施事項 | 処理内容 | プログラムファイル | 使用する関数 |
| --- | --- | --- | --- | --- |
| 1 | 操作内容の判定 | 対象環境・操作・実行区分を解釈し、一時環境の作成・変更処理を選択する。 | `tools/environment.py` | `main`、`execute` |
| 2 | 管理情報への接続・管理対象の確認 | 一時環境のTerraformを初期化し、既存の管理対象を取得する。 | `tools/environment.py` | `initialize`、`state_list` |
| 3 | 配布資材の作成 | Lambdaのプログラムと依存ライブラリを配布用ZIPにまとめる。 | `tools/deployment/build.py` | `build` |
| 4 | 既存設定の取得 | 既存のコンテナイメージ、SFTPホスト公開鍵、日次処理の有効状態等を取得し、Terraformへの入力値を準備する。 | `tools/environment.py` | `temporary_inputs`、`resources` |
| 5 | 事前の変更計画の表示 | `plan`の場合、変更計画を作成・表示して終了する。初回はSFTPサーバ等の先行構築範囲に限定する。 | `tools/environment.py` | `execute`、`plan`、`tf` |
| 6 | 共有セキュリティ設定の管理状況確認 | `apply`の場合、実際の設定とStateを照合し、他用途で管理されている設定との競合がないことを確認する。 | `tools/status/security_inventory.py` | `inventory`、`assert_owned_security` |
| 7 | アプリケーションの版の確定 | コンテナイメージを作成してECRへ登録し、後続処理で使用する版を確定する。 | `tools/environment.py` | `apply_temporary`、`run`、`aws` |
| 8 | ファイル連携先の基盤整備 | SFTPサーバ、認証情報の保存先、先行して必要なセキュリティ設定等を整備する。 | `tools/environment.py` | `apply_temporary`、`apply` |
| 9 | ファイル連携先の接続設定 | SSMで操作可能になるまで待機する。既存のSFTP設定を確認し、必要時に初期設定を行い、実サーバのホスト公開鍵を取得する。 | `tools/environment.py`、`tools/deployment/setup_sftp.py` | `apply_temporary`、`ensure`、`ssm_command`、必要時に`setup` |
| 10 | DB更新用の環境整備 | 初回はWebを起動せずに基盤を整備する。既存環境の更新時は、DB更新用タスク定義と依存先を先行して反映する。 | `tools/environment.py` | `apply_temporary`、`apply` |
| 11 | DB更新処理の起動・結果確認 | ECSでDB更新用タスクを起動し、停止と終了コード0を確認する。失敗した場合は後続処理を停止する。 | `tools/shared/deployment_runtime.py` | `task` |
| 12 | DBの構造・権限の更新 | ECSタスク内で未適用のSQLを適用し、アプリケーション・Web用DBユーザの権限を設定する。 | `02_資材/02_temporary/app/tools/migrate.py` | `migrate`、`roles` |
| 13 | 全体構成・Webの反映 | DB更新の成功後に全体構成を反映する。初回はWebを2台で起動する。 | `tools/environment.py` | `apply_temporary`、`apply`、`aws` |

番号12のみ、各構成のルートからのパスを記載する。番号12は、番号11で起動したECSタスク内で実行する。

番号6〜13は`apply`の場合のみ実施する。`apply_temporary`が各処理の実行順序を制御し、各段階のTerraform適用では、その実行内で計画を作成して適用する。

初回の事前計画は環境全体を対象としない。また、既存環境の事前計画では既存のコンテナイメージを参照するため、新しいイメージへの変更は`apply`内で計画する。

更新時は既存Webを維持した状態でDBを更新するため、DB変更は既存Webとの互換性を必須とする。

`apply`の正常終了時は、構成反映・SFTP設定・DB更新が完了した状態とする。画面・API・ファイル連携等の正常動作は、別途動作確認で判定する。

## 7. 環境操作：一時環境削除

利用終了後の一時環境を削除し、再作成に必要な常設環境を保持しつつ費用を抑制する。

| 番号 | 実施事項 | 処理内容 | プログラムファイル | 使用する関数 |
| --- | --- | --- | --- | --- |
| 1 | 操作内容の判定 | 対象環境・操作・実行区分を解釈し、一時環境の削除処理を選択する。 | `tools/environment.py` | `main`、`execute` |
| 2 | 管理情報への接続 | 一時環境のTerraformを初期化し、S3に保存した管理情報へ接続する。 | `tools/environment.py` | `initialize` |
| 3 | 削除対象の確認 | 一時環境の管理対象を取得する。対象が存在しない場合は終了する。 | `tools/environment.py` | `state_list` |
| 4 | 計画用資材の作成 | Terraformが削除計画の作成時に参照するLambda ZIPを作成する。 | `tools/deployment/build.py` | `build` |
| 5 | 計画用設定の準備 | 既存構成の設定値を取得し、削除計画で使用する入力値を準備する。 | `tools/environment.py` | `temporary_inputs`、`resources` |
| 6 | 削除計画の作成・表示 | 一時環境の削除計画を作成し、対象を表示する。`plan`の場合は表示して終了する。 | `tools/environment.py` | `execute`、`tf` |
| 7 | 一時環境の削除 | `apply`の場合、同じ実行内で作成した削除計画を適用する。 | `tools/environment.py` | `execute`、`tf` |

リソース間の削除順序はTerraformが制御する。コンテナイメージの作成・登録、SFTP初期設定、DB更新は実施しない。

ログも削除対象とし、DBの最終スナップショットは作成しない。KMS鍵等の削除予約を伴うリソースは、AWS側の待機期間に従う。

`apply`の正常終了時は、一時環境の管理対象に対する削除処理が完了した状態とする。常設環境は保持する。

## 8. ワークフロー③：Terraform状態確認

常設環境・一時環境について、Terraformの管理対象と、定義に対する構成差分を確認する。

| 番号 | 実施事項 | 処理内容 | プログラムファイル | 使用する関数 |
| --- | --- | --- | --- | --- |
| 1 | 起動条件・権限・同時実行制御 | mainブランチから手動起動する。権限および同時実行制御は、3.1節の番号2・3と共通とする。`plan`／`apply`の選択は行わない。 | `.github/workflows/03_aws-status.yml` | ―（YAML定義） |
| 2 | 実行環境の準備・AWS認証 | 3.1節の番号4〜9と同じ処理で、Ubuntuランナー、コード、実行用ソフトウェアを準備し、AWSへ認証する。 | `.github/workflows/03_aws-status.yml`、`.github/actions/workflow-runtime/action.yml` | ―（YAML定義・Action） |
| 3 | 常設環境の管理対象確認 | 常設環境の管理情報へ接続し、管理対象を表示する。対象が存在しない場合は、その旨を表示して常設環境の確認を終了する。 | `tools/environment.py` | `main`、`execute`、`initialize`、`state_list` |
| 4 | 常設環境の構成差分確認 | 現在の構成とTerraform定義を比較し、差分を表示する。 | `tools/environment.py` | `persistent_inputs`、`execute`、`tf` |
| 5 | 一時環境の管理対象確認 | 一時環境の管理情報へ接続し、管理対象を表示する。対象が存在しない場合は、その旨を表示して一時環境の確認を終了する。 | `tools/environment.py` | `main`、`execute`、`initialize`、`state_list` |
| 6 | 一時環境の比較用資材・設定の準備 | Lambda ZIPを作成し、既存設定を取得して比較用の入力値を準備する。 | `tools/environment.py`、`tools/deployment/build.py` | `temporary_inputs`、`resources`、`build` |
| 7 | 一時環境の構成差分確認 | 現在の構成とTerraform定義を比較し、差分を表示する。 | `tools/environment.py` | `execute`、`tf` |
| 8 | 実行結果の表示 | 各環境の確認結果をGitHub Actionsの実行画面に表示する。 | `.github/workflows/03_aws-status.yml`、`tools/environment.py` | `main`、`execute` |

`.github/`のパスは、各構成のルートから記載する。

常設環境の確認に失敗した場合も、一時環境の確認を試みる。ただし、ワークフローのキャンセル時は実行しない。

差分の検出は確認結果として扱い、自動修正は行わない。確認範囲はTerraformの管理対象とし、AWSアカウント全体のリソース調査や、画面・DB・SFTPの動作確認は含まない。差分があっても確認自体は成功とする。成功は「差分なし」を意味しない。

## 9. 共通の実行条件

| 項目 | 仕様 |
| --- | --- |
| 事前設定 | Repository Variable `AWS_ROLE_ARN`・`TF_STATE_BUCKET`を設定する。通知先`NOTIFICATION_EMAIL`はRepository Variablesに設定する。常設環境・一時環境の作成・変更のapplyでは通知先を必須とする。 |
| 実行時間上限 | CIは10分、環境操作・状態確認は90分とする。 |
| 実行競合の防止 | 環境操作・状態確認は`portfolio-environment`で直列化する。実行中ジョブを自動キャンセルせず、`queue: max`で最大100件を保留する。TerraformのS3 lockfileも併用する。依存する操作は前の実行完了後に起動する。 |
| State保存先 | `TF_STATE_BUCKET`の`aws-cicd-portfolio/persistent/terraform.tfstate`と`aws-cicd-portfolio/temporary/terraform.tfstate`へ分離する。 |
| Terraform作業先 | 常設環境は`02_資材/01_persistent`、一時環境は`02_資材/02_temporary/terraform`とする。 |
| planとapply | 別の実行の事前planは引き継がず、apply内で再計画して同じ実行内の保存計画を適用する。事前planと実行時planの一致は保証しない。追加の承認待ちは設けない。 |
| 適用範囲 | applyは作成・変更・置換・定義から削除された資源の削除を含む。`No changes`も正常とする。一時環境では段階全体の実行指示となる。 |
| 空State | 状態確認・削除では`EMPTY_STATE`を表示して正常終了する。Stateの読取エラーは空と扱わず失敗とする。 |
| 実行資材 | Pythonモジュール検索先と依存ライブラリは共通Actionで準備する。初回plan用の仮鍵・保存計画はアクセス権を制限した一時領域へ置き、終了時に削除する。 |

## 10. 実行順序の理由と方式の選択

TerraformはAWSリソースの構成とリソース間の依存関係を管理する。Pythonはリソース作成後に確定する値の取得と、外部処理の完了確認を制御する。

| 実施順序 | 理由 |
| --- | --- |
| Lambda ZIP作成 → Terraform計画・適用 | 定義が参照する配布物とハッシュを先に用意する必要がある。 |
| 共有セキュリティ設定の所有確認 → ECR登録・基盤変更 | 他用途の設定との競合を変更前に検出する必要がある。 |
| Docker build・ECR登録 → 使用イメージの確定 | 新しいイメージのdigestは登録後に確定する。 |
| SFTPサーバ・Secret作成 → SFTP設定 → Connector適用 | 実ホスト公開鍵はサーバ作成後に取得する必要があり、計画用仮鍵では接続先を検証できない。 |
| DB・更新用タスク準備 → DB更新成功確認 → 新Web反映 | リソースの存在だけではSQL適用の成功を判定できない。初回はWeb起動を抑制し、更新時は既存Webと互換性のあるDB変更を先行する。 |
| 段階適用 → 最後の全体適用 | 先行対象に限定した適用後、対象指定を外して全体構成を反映する必要がある。 |
| 一時環境削除 → 常設環境削除 | Stateが別であり、共通基盤への依存を各State内の依存グラフだけでは制御できない。 |

GitHub Actionsで起動・認証・排他、Pythonで外部処理の順序、TerraformでAWS構成を管理する。各YAMLへDocker・SSM・DB処理を複製する方式は、変更時の整合維持が難しいため採用しない。Terraformのlocal-execへ外部処理を集約する方式、および1回のapplyのみで全処理の完了を判定する方式も採用しない。失敗箇所と副作用を追跡しやすい一方、複数回の計画・適用と、中断後の復旧判断が必要となる。

更新時に既存Webを残す順序だけで完全無停止を保証しない。DB互換性、ECSヘルスチェック、利用中接続への影響は別途確認する。

## 11. 異常時・再実行・確認範囲

| 失敗箇所 | 停止後に確認する事項 |
| --- | --- |
| State接続・取得 | バケット・S3キー・IAM権限。取得失敗を未作成とみなさない。 |
| 共有設定の所有確認 | 実AWSとStateの管理状況。他用途の設定を無断で取り込まない。 |
| Docker登録・digest取得 | ECRへ登録済みのイメージが残っている可能性。 |
| SFTP先行構築・設定 | 作成済みEC2・Secret・ホスト鍵とStateの整合。 |
| DB更新 | 成功済みSQL、履歴・checksum、DB権限、Secret。新Web反映へは進まない。 |
| 最終構成反映・Web起動 | 部分的に完了した構成と現在のState・実AWSの状態。 |
| 常設環境削除の拒否 | 一時環境の残存、または旧TLSポリシー管理情報。旧情報は常設環境の作成・変更をplan・applyして分離後、削除を再実行する。 |

成功済みの構成反映・ECR登録・SFTP設定・DB更新を自動的に巻き戻さない。再実行は入口から行い、既存State・SFTP設定・SQL履歴を参照する。失敗行からの単純な続行ではない。

CIは構文・書式・定義とAWSに接続しない模擬実行の合格を示す。applyは各操作で定義した構成反映・初期設定の完了を示す。画面・API・DB接続・SFTP・業務処理の正常動作、通知受信、セキュリティ評価の完了は別途確認する。状態確認はTerraform管理対象に限り、AWSアカウント全体の残存調査は含まない。
