# 操作手順

各runの完了を待ってから次を起動する。環境操作と状態確認は共通の排他グループで直列化する。

GitHubのActions画面で「02_環境操作」を選択し、Run workflow → Branch `main` → stack（対象環境）→ operation（操作）→ mode `plan` → Run workflowの順に操作する。計画のログを確認した後、同じstack・operationとmode `apply`を指定して別runを起動する。

| 用途 | 実行順 |
| --- | --- |
| 新規作成 | persistent / apply / plan→apply、temporary / apply / plan→apply |
| 構成・イメージ変更 | 変更資材をmainへ反映し、対象stack / apply / plan→apply |
| 一時環境のみ削除 | temporary / destroy / plan→apply |
| 全削除 | temporary / destroy / plan→apply、persistent / destroy / plan→apply |
| 状態確認 | 03_Terraform状態確認（入力なし） |

operationのapplyは作成・変更、modeのapplyは選択した操作の実行を意味する。削除はoperation=`destroy`かつmode=`apply`の場合に実行する。実行名にもstack・operation・modeを表示する。

一時環境の初回planはSFTP等の先行構築範囲のみを対象とする。残る計画はapply内で段階的に生成する。事前planと実行時planの一致は保証しない。[ワークフロー概要](01_ワークフロー概要.md)に制約を示す。

apply後は環境を保持する。利用終了後は一時環境、必要に応じて常設環境を削除する。State用S3とOIDC実行基盤は保持する。全削除後は03で両StateのEMPTY_STATEを確認する。03はStateと定義差分の確認であり、アプリの稼働確認やAWS全体の残存調査ではない。

失敗時はエラーのあるステップと直前のログを確認し、原因を解消して同じ操作を再実行する。

## 実行前の確認

ワークフロー概要第9章のAWSロール・Stateバケット・通知先を設定する。変更資材がmainへ反映され、対象リビジョンのCIが成功していることを確認する。apply内に追加の承認待ちはなく、事前planの保存ファイルは引き継がない。

## 結果確認・失敗時対応

Actionsで対象の実行名、stack・operation・mode、コミットを確認し、各ステップのログと終了結果を確認する。状態確認は差分ありでも成功するため、成功表示だけで差分なしと判断しない。apply後のアプリ動作・通知受信等は別途確認する。

失敗した場合は、概要第11章に従って成功済みの変更と現在のStateを確認する。原因を解消して同じ操作を入口から再実行する。DB更新失敗時はSQL履歴・checksum・Secret・権限を確認し、未確認のままDBを復元しない。
